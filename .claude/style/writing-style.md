# Part 1 · 硬规则(必须遵守)

## 1.1 Frontmatter 与文件命名

每篇文章**必须**包含 YAML frontmatter,必填 `title` / `chapter` / `order`。文件命名 `{序号}-{kebab-case}.md`,`order` 与文件名序号一致。完整字段与标签体系见 [`.claude/rules/documents-frontmatter.md`](../rules/documents-frontmatter.md)。

```yaml
---
title: "文章标题"
description: "一句话描述这篇文章的核心内容"
chapter: 0
order: 0
tags:
  - host              # platform(必填 1 个)
  - cpp-modern        # topic(必填 ≥1 个)
  - beginner          # difficulty(必填 1 个): beginner | intermediate | advanced
difficulty: beginner
reading_time_minutes: 10
platform: host
cpp_standard: [11, 14, 17, 20]
---
```

## 1.2 文章骨架

不同文章类型用不同骨架,任选其一;骨架是参考不是填空模子,按组件/主题特性裁剪。

**通用文章**:

```
# 文章标题

## 引言(动机段)

## 核心概念(分小节展开)

## 代码示例(可编译运行,标注 Platform 和 C++ Standard)

## 实战应用

## 注意事项(含常见错误表)

## 小结(含关键要点 checklist)

## 练习(可选)

## 参考资源(cppreference 优先,标注标准版本)
```

**嵌入式平台教程**:本章目标 → 硬件原理(只讲本章 feature)→ HAL 接口 → 最小 Demo → C++23 封装 → 常见错误 → 练习题 → 可复用代码片段 → 本章小结。

**参考卡**:一句话 → 头文件 → 核心 API 速查表 → 最小示例(≤20 行)→ 嵌入式适用性 → 编译器支持表 → 另见。

**标准库组件深入**:标题主题驱动(点出最值得讲透的机制,不用"第一步/第二步")、平实切入、"上手跑一跑"实测收口、参考资源收尾;教学点按该组件读者最易踩的错误取舍,不求全列。

**Lab / 练习**(CS144 风格):目标 → 前置知识 → 工程脚手架(指向 `code/` 下可构建工程)→ 最终接口 → 3-5 个 milestone(每个:目标/为什么/实现指引/验证)→ 性能测试 → 扩展练习 → 自查清单。验证必须是可编译、补全实现后能变绿的真实测试;并发 Lab 用 TSan 验证。

## 1.3 代码风格

与项目 `.clang-format` 一致:

```
文件命名:snake_case        → gpio_input.cpp
类命名:  PascalCase        → GpioPin, UartDriver
函数命名:snake_case        → configure_pull_up()
常量命名:kPascalCase       → kMaxRetryCount
宏命名:  UPPER_SNAKE_CASE → CONFIG_UART_BAUDRATE
模板参数:PascalCase        → typename TPin
枚举值:  kPascalCase       → enum class PullMode { kUp, kDown, kNone }
```

- Include 分组:对应头文件 → C++ 标准库 → 第三方 → 项目内,组间空行、组内字母序
- 缩进 4 空格,行宽 100;函数定义大括号换行开,控制语句同行开;指针/引用靠左(`int* p`)
- 注释解释"为什么"而非"做什么";Doxygen 格式用于 API 文档

## 1.4 技术表达与验证铁律(关乎正确性,必须执行)

- **必须用真实证据**:真实命令行输出、原始代码、编译日志、串口日志。**禁止编造输出。**
- **必须解释"为什么"**,禁止只给步骤("这是因为……""底层机制是……")
- **必须实验验证收口**:用真实输出/汇编/sizeof 佐证,不空口断言;凡断言 C++ 行为先编译实测或查 cppreference 并标标准版本
- **必须含风险提示**:关键技术点要有提示块(`::: warning`),语气见 Part 2

## 1.5 行为底线(铁律)

禁粗口;禁攻击性语言;禁阴阳怪气读者。

# Part 2 · 声音要点(目标方向)

本教程的声音:**一位正在亲自折腾 C++ / 底层 / 系统的工程师博主**——会连续熬夜、会吐槽旧方案、会展示自己的误判、会给出实战验证输出。技术判断最终落到源码、日志、实验、汇编或标准条款上。不是中性技术文档,也不是表演式段子。

- **人称跟着关系走**:讲亲历、判断和误判用「笔者」(作者一个人扛的事);和读者一起观察、动手、推导用「咱们」;直接接住读者可用「您」。连续的技术解释里要看得见作者在场,不能整段退化成无人的说明书
- **正文以散文为主**:列表只用于真正的对比、参考资源和严格步骤;正文论点和小结不要排成整齐的项目表
- **偏长句子,大段代码按逻辑分段**:顺着功能顺序拆小段,逐步讲"为什么这么写、要注意什么"
- **概念按认知顺序登场**:先给对象本身,再给代称和比喻;不能让人猜"这台机器""这笔账"指什么
- **允许文字呼吸**:可以突然插话、吐槽、自嘲、重复一句;插话要接着眼前发生的事,说完回到技术问题
- **不编故事**:确实发生过的误判、返工可以完整写;没发生过就不要为了戏剧感虚构事故
- **不刻意提炼金句**:不替每段写总结,不在结尾把全文整理成"三层、三件事、一个答案"
- **先写清楚,再去 AI 味**:不为避开某个词换成更生硬的句子,也不为显得有风格而造比喻、对仗

常用衔接:「我们现在要做的是」「先别急」「这里先验证一下」「你会发现」「接下来问题来了」「真正的风险在后面」。验证口吻:「来验证一下」「我们试跑一下」「输出如下」。

> 人类贡献者能贴合就贴合,不强求,维护者会朝这个方向编辑;Part 1 硬规则才是准入门槛。AI 生成内容请把本卡当作目标尽量贴合,参考其中的例子而非只读描述。
