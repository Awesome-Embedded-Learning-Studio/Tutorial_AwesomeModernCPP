# std::function, std::invoke, and Callable Objects

While writing an event system, we ran into a very practical problem: storing callbacks of every shape and kind—plain functions, member functions, lambdas, functors, the whole zoo. Function pointers can only point to static or global functions and can't carry any context; and if you store a lambda with `auto`, every lambda has a distinct type, so they can't live in the same container. `std::function` solves this—with type erasure, it unifies all kinds of callable objects into a single type. But type erasure comes at a cost, so the question becomes: how large is that cost exactly? And is there a way to get the best of both worlds?

In this chapter we start with the internal machinery of `std::function`, then move on to `std::invoke`, the "universal invoker", and finally talk about zero-overhead callback design—finding the balance point between type safety and performance.

---

## The Complete Family of C++ Callable Objects

Before diving into the machinery, let's first sort out what forms "callable objects" actually take in C++. A callable object is anything you can call with `()` syntax (or with `std::invoke`). Plain functions and function pointers are the most basic—you call them directly, or indirectly through a pointer. A functor is a class object with an overloaded `operator()`. A lambda is an anonymous functor generated by the compiler. A pointer to member function points at a class's member function and needs an object instance to be invoked. On top of these, there are objects wrapped in `std::function` and the results of `std::bind`.

The problem is that these callables each have different invocation syntax—plain functions are called directly, member functions need `obj.*ptr` or `obj->*ptr`, and functors and lambdas are called like `f(args)`. If you wanted to write a generic function that "invokes all of these uniformly", before C++17 you had to write a pile of template specializations; with `std::invoke`, one function does the job.

---

## std::function: A Function Container Built on Type Erasure

`std::function` is the general-purpose function wrapper introduced in C++11, defined in the `<functional>` header. It can store, copy, and invoke any callable object that matches the required signature. Its core capability is exactly one thing: **unifying callable objects of different types into a single type**.

```cpp
#include <functional>
#include <iostream>

int add(int a, int b) { return a + b; }

struct Multiplier {
    int factor;
    int operator()(int x) const { return x * factor; }
};

void demo_std_function() {
    std::function<int(int, int)> func;

    // Store a plain function
    func = add;
    std::cout << func(3, 4) << "\n";   // 7

    // Store a lambda
    func = [](int a, int b) { return a * b; };
    std::cout << func(3, 4) << "\n";   // 12

    // Store a functor
    func = Multiplier{5};
    std::cout << func(10) << "\n";     // Compile error: signature mismatch
    // Multiplier's operator() takes only one argument, but func's signature is int(int,int)
}
```

### The Type Erasure Mechanism

How does `std::function` stuff things of different types into the same shell? The answer is type erasure. The simplified idea: internally, `std::function` defines an abstract base class (the Concept) that declares a pure virtual `invoke`; then for each concrete callable type it generates a derived class (the Model) that implements `invoke`. `std::function` holds a pointer to the Concept, and each call is dispatched through the virtual function to the concrete implementation.

We can simulate this process in code:

```cpp
#include <memory>
#include <utility>

// A simplified sketch of how std::function works
template<typename Signature>
class SimpleFunction;

template<typename R, typename... Args>
class SimpleFunction<R(Args...)> {
    // Abstract interface
    struct ICallable {
        virtual ~ICallable() = default;
        virtual R invoke(Args... args) = 0;
        virtual ICallable* clone() const = 0;
    };

    // Concrete implementation: a templated derived class storing the real callable
    template<typename T>
    struct CallableImpl : ICallable {
        T callable;
        explicit CallableImpl(T c) : callable(std::move(c)) {}

        R invoke(Args... args) override {
            return callable(std::forward<Args>(args)...);
        }

        ICallable* clone() const override {
            return new CallableImpl(callable);
        }
    };

    ICallable* ptr_ = nullptr;

public:
    SimpleFunction() = default;

    template<typename T>
    SimpleFunction(T callable)
        : ptr_(new CallableImpl<std::decay_t<T>>(std::move(callable))) {}

    SimpleFunction(const SimpleFunction& other)
        : ptr_(other.ptr_ ? other.ptr_->clone() : nullptr) {}

    ~SimpleFunction() { delete ptr_; }

    R operator()(Args... args) {
        return ptr_->invoke(std::forward<Args>(args)...);
    }
};
```

From this sketch you can see the three ingredients of type erasure: a unified abstract interface (`ICallable`), a templated concrete implementation (`CallableImpl<T>`), and a pointer to the interface (`ptr_`). At storage time the type information is "erased"—the outside world sees only `ICallable*`; at call time it is brought back through the virtual function table.

### Small Object Optimization (SBO)

The simplified version above has an obvious problem: every construction does a heap allocation with `new`. For a small lambda capturing one or two `int`s, that heap allocation may cost more than the lambda itself. So real `std::function` implementations all use small object optimization (Small Buffer Optimization, also known as SBO or SOO): a fixed-size buffer (usually 16-32 bytes) is reserved inside the `std::function` object, and if the wrapped callable is small enough, it is stored directly in that buffer, with no heap allocation.

```cpp
#include <functional>
#include <iostream>
#include <array>

void demo_sbo_size() {
    // A small lambda: usually fits in the SBO buffer
    auto small = [x = 42]() { return x * 2; };
    std::function<int()> f1 = small;
    std::cout << "sizeof(std::function<int()>): "
              << sizeof(f1) << " bytes\n";
    // Usually 32-64 bytes (implementation-dependent)

    // A large lambda: exceeds the SBO buffer and triggers a heap allocation
    auto large = [data = std::array<int, 100>{}]() {
        return data.size();
    };
    std::function<std::size_t()> f2 = large;
    std::cout << "sizeof(std::function<size_t()>): "
              << sizeof(f2) << " bytes\n";
    // Same size, but with an internal heap allocation

    // For comparison: the size of a function pointer
    std::cout << "sizeof(void(*)()): "
              << sizeof(void(*)()) << " bytes\n";
    // Usually 8 bytes (on 64-bit systems)
}
```

Let's actually measure libstdc++'s SBO behavior. On GCC 15.2.1, `std::function<int()>` is 32 bytes. But the test results show that a lambda capturing a single `int` (a closure object of just 4 bytes) does not trigger a heap allocation, while a lambda capturing 5 `int`s or a pointer does get allocated—suggesting that GCC 15.2's SBO implementation is rather conservative, probably reserving extra space for the virtual table pointer and management metadata. libc++'s (Clang's) implementation may differ; the exact behavior varies by version.

> **Verification code**: `code/volumn_codes/vol2/ch03-lambda/test_sbo_size.cpp` (GCC 15.2.1, `-O2`)
>
> **Important**: SBO behavior varies widely across compilers and versions. If your code is performance-sensitive, prefer template parameters or hand-written type erasure to get predictable behavior.

## Function Pointers: Zero Overhead but Limited

Before we get to zero-overhead alternatives, let's first revisit function pointers. Function pointers are a mechanism inherited from the C era: they point straight at a code address, simple and efficient. The size is just one pointer (8 bytes on a 64-bit system), and a call is a single `call` instruction (`call *%rax`), with no extra layer of indirection.

> **Measured performance**: In our tests (GCC 15.2.1, `-O2`), calls through a function pointer were about 30% slower than a direct call (1.29x). That's because a direct call can be fully inlined into the computation instructions, while a function pointer still needs an indirect `call`. In unoptimized code, however, both need a `call` instruction, and the gap narrows.
>
> **Verification code**: `code/volumn_codes/vol2/ch03-lambda/test_function_performance.cpp`

```cpp
// Declaring and assigning a function pointer
int (*func_ptr)(int, int) = [](int a, int b) { return a + b; };

// Simplify the type name with using
using BinaryOp = int(*)(int, int);
BinaryOp op = [](int a, int b) { return a + b; };
int result = op(3, 4);   // 7
```

The biggest limitation of function pointers is that they cannot carry context—they can only point to captureless lambdas (or plain functions and static member functions). Any lambda with captures cannot be converted to a function pointer. When you need to pass a `this` pointer or some state along to the callback, function pointers are simply out of their depth.

```cpp
// A captureless lambda can be converted to a function pointer
int (*fp1)(int, int) = [](int a, int b) { return a + b; };  // OK

// A lambda with captures cannot be converted
int x = 42;
int (*fp2)(int, int) = [x](int a, int b) { return a + b + x; };  // Compile error
```

| Feature | Function Pointer | std::function |
|------|----------|---------------|
| Size | 8 bytes (64-bit) | 32-64 bytes |
| Heap allocation | None | Triggered beyond the SBO range |
| Indirection layers | 1 (direct call) | 1 (virtual table indirection) |
| Carries context | No | Yes |
| Inlining-friendly | Yes | Poor (type erasure gets in the way) |
| Performance (vs. direct call) | ~1.3x | ~7-9x |

## std::invoke: A Unified Invocation Interface

`std::invoke`, introduced in C++17 (defined in `<functional>`), is a "universal invoker". Whatever kind of callable object you have—a plain function, a pointer to member function, a lambda, a functor—`std::invoke` invokes it with the same syntax. It implements the semantics of the INVOKE expression defined in the standard:

```cpp
#include <functional>
#include <iostream>

struct Widget {
    void greet(const std::string& msg) {
        std::cout << "Widget says: " << msg << "\n";
    }
    int data = 42;
};

void free_func(int x) {
    std::cout << "free_func: " << x << "\n";
}

void demo_invoke() {
    Widget w;

    // Plain function
    std::invoke(free_func, 42);

    // Functor / lambda
    std::invoke([](int x) { std::cout << "lambda: " << x << "\n"; }, 99);

    // Pointer to member function + object
    std::invoke(&Widget::greet, w, "hello");

    // Pointer to data member + object (can be read and modified)
    int val = std::invoke(&Widget::data, w);
    std::invoke(&Widget::data, w) = 100;
}
```

Look at that member function call—the traditional spelling is `(w.*(&Widget::greet))("hello")` or `(wg.*mem_func)("hello")`, syntax we have to look up every single time we write it. With `std::invoke` it's just `std::invoke(mem_func, obj, args...)`. Far cleaner.

### How invoke Works Under the Hood

The implementation of `std::invoke` isn't complicated; at its core it is compile-time type discrimination and dispatch. For ordinary callable objects (function pointers, lambdas, functors), it calls `f(args...)` directly; for pointers to member functions, it picks the right invocation syntax based on the object's category (pointer, reference, or `reference_wrapper`); for pointers to data members, it returns a reference to the corresponding member. All of these decisions are made at compile time—zero runtime overhead.

### std::invoke_result_t

C++17 also provides the companion `std::invoke_result_t`, which yields the return type of a `std::invoke` call at compile time. When writing generic code, this tool is remarkably practical:

```cpp
#include <type_traits>
#include <functional>

template<typename Func, typename... Args>
auto safe_call(Func&& func, Args&&... args)
    -> std::invoke_result_t<Func, Args...>
{
    using Ret = std::invoke_result_t<Func, Args...>;

    if constexpr (std::is_void_v<Ret>) {
        std::invoke(std::forward<Func>(func), std::forward<Args>(args)...);
        std::cout << "(void return)\n";
    } else {
        Ret result = std::invoke(std::forward<Func>(func),
                                 std::forward<Args>(args)...);
        std::cout << "result: " << result << "\n";
        return result;
    }
}
```

### invoke's Performance

When you use `std::invoke` in template code, the compiler sees the entire call chain and inlines it down to the same level as a direct call. We measured it: under `-O2` optimization, `std::invoke` calls perform exactly the same as direct calls (within measurement error—they can even come out slightly faster due to test noise). That's because `std::invoke` itself is just a thin compile-time dispatch wrapper that gets fully inlined away under optimization.

> **Verification code**: `code/volumn_codes/vol2/ch03-lambda/test_invoke_performance.cpp`
>
> **Assembly verification**: Generating assembly (`g++ -O2 -S`) shows that direct calls, `std::invoke`, function pointers, and lambdas all compile to exactly the same code—compute the result directly and return it, with no `call` instruction.

Of course, if you call through a callable stored in a `std::function`, the indirection overhead comes from `std::function`'s type erasure, not from `std::invoke`.

## Zero-Overhead Callback Design: Templates + Lambdas

Once you understand where `std::function`'s overhead comes from (type erasure, possible heap allocation, indirect calls), the question becomes: in many scenarios the callback's type is already fixed at registration time—can we skip type erasure altogether?

The answer is yes. The simplest zero-overhead approach is to pass the lambda directly as a template parameter—the compiler knows the full closure type, and the call is fully inlined:

```cpp
#include <algorithm>
#include <vector>
#include <iostream>

// A template parameter accepts any callable object: zero overhead
template<typename Callback>
void for_each_if(std::vector<int>& data, Callback pred, Callback action) {
    for (auto& elem : data) {
        if (pred(elem)) {
            action(elem);
        }
    }
}

void demo_template_callback() {
    std::vector<int> data = {1, 2, 3, 4, 5, 6, 7, 8};

    int threshold = 5;
    int sum = 0;

    // Lambdas passed straight to template parameters, fully inlined
    for_each_if(data,
        [threshold](int x) { return x > threshold; },   // predicate
        [&sum](int& x) { sum += x; }                     // action
    );

    std::cout << "Sum of elements > " << threshold << ": " << sum << "\n";
    // Output: Sum of elements > 5: 21 (6+7+8)
}
```

The problem with this approach: every distinct lambda type instantiates a distinct template function, so you cannot put callbacks of different types into the same container. If your design genuinely needs runtime polymorphism (say, an event queue storing callbacks of all kinds), then some form of type erasure is unavoidable.

### Manual Type Erasure: A Function Pointer Table Instead of Virtual Functions

If you need type erasure but want to avoid the full cost of `std::function`, you can hand-write a lightweight type-erased container. The core idea: replace the virtual function table with a table of function pointers, and replace heap allocation with a fixed-size on-stack buffer:

```cpp
#include <cstddef>
#include <utility>
#include <iostream>
#include <new>

template<typename Signature, std::size_t BufSize = 32>
class LightCallback;

template<typename R, typename... Args, std::size_t BufSize>
class LightCallback<R(Args...), BufSize> {
    // Operation table: function pointers instead of virtual functions
    struct VTable {
        void (*move)(void* dst, void* src);
        void (*destroy)(void* obj);
        R (*invoke)(void* obj, Args... args);
    };

    // A dedicated VTable generated for each callable type
    template<typename T>
    struct VTableFor {
        static void do_move(void* dst, void* src) {
            new(dst) T(std::move(*static_cast<T*>(src)));
        }
        static void do_destroy(void* obj) {
            static_cast<T*>(obj)->~T();
        }
        static R do_invoke(void* obj, Args... args) {
            return (*static_cast<T*>(obj))(std::forward<Args>(args)...);
        }
        static constexpr VTable value{do_move, do_destroy, do_invoke};
    };

    alignas(std::max_align_t) unsigned char storage_[BufSize];
    const VTable* vtable_ = nullptr;

public:
    LightCallback() = default;

    template<typename T>
    LightCallback(T&& callable) {
        using Decay = std::decay_t<T>;
        static_assert(sizeof(Decay) <= BufSize, "Callable too large for buffer");
        static_assert(alignof(Decay) <= alignof(std::max_align_t),
                     "Callable alignment too high");
        new(storage_) Decay(std::forward<T>(callable));
        vtable_ = &VTableFor<Decay>::value;
    }

    LightCallback(LightCallback&& other) noexcept : vtable_(other.vtable_) {
        if (vtable_) {
            vtable_->move(storage_, other.storage_);
            other.vtable_ = nullptr;
        }
    }

    ~LightCallback() {
        if (vtable_) vtable_->destroy(storage_);
    }

    LightCallback(const LightCallback&) = delete;
    LightCallback& operator=(const LightCallback&) = delete;

    R operator()(Args... args) {
        return vtable_->invoke(storage_, std::forward<Args>(args)...);
    }

    explicit operator bool() const { return vtable_ != nullptr; }
};

void demo_light_callback() {
    int multiplier = 3;
    LightCallback<int(int), 32> cb = [multiplier](int x) {
        return x * multiplier;
    };

    std::cout << cb(14) << "\n";  // 42
}
```

This `LightCallback` is not as general as `std::function` (no copy support, no allocator support), but it covers the most common use case: storing lambdas with captures, with no heap allocation and a single layer of indirection. In embedded or high-performance scenarios, this "just good enough" design is usually the most pragmatic choice.

### Selection Guide

To sum up the trade-offs among callback storage options. Function pointers suit scenarios that need no context: zero overhead, but they can only point to captureless lambdas or plain functions. `std::function` suits scenarios that need runtime polymorphism: general-purpose, but with a significant performance cost—even when the object fits within the SBO range, the virtual table indirection still blocks inlining, measuring 7-9x slower than a direct call. Template parameters suit scenarios where the type is known at compile time: fully zero overhead, but not storable in containers. Hand-written type erasure suits scenarios that need runtime polymorphism plus performance: a bit more code, but under your control.

> **Performance data source**: `code/volumn_codes/vol2/ch03-lambda/test_function_performance.cpp` (GCC 15.2.1, `-O2`, 100 million calls)

```cpp
// 1. No context, hot path: function pointer
void fast_path(int (*cb)(int)) { cb(42); }

// 2. With context, general-purpose scenario: std::function
void generic_path(std::function<void(int)> cb) { cb(42); }

// 3. Type known at compile time: template parameter
template<typename CB>
void zero_cost_path(CB&& cb) { cb(42); }

// 4. With context, high performance: manual type erasure
void optimized_path(LightCallback<void(int), 24> cb) { cb(42); }
```
