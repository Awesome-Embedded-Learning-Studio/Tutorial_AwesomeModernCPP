# OS 线程与开销

第 4 章的主业是无锁数据结构与性能实测，动手之前，咱们先往机器那边走一层，把一个从第 0 章就悬着的问题量清楚：您写下 `std::thread t(func)` 的时候，操作系统那边发生了什么，又花掉了什么。空线程的成本得用微秒来计，这个数值多少、怎么量，就是本篇的正题。

有三件事得先说在明处：开销数字**没有放之四海的定值**，机器、内核版本、当时的负载，掺进来的每一手都不一样，所以数表咱们不背，本篇交给您的是一套往自己机器上量数的办法；数字的讲法照卷首页的约定作数，占位没填上的时候，那句话咱们就当没说过；至于对错，那是 [TSan 那篇](../ch00-concurrency-fundamentals/02-data-race-and-tsan.md)的尺子，本篇管的是贵贱。

路线是三站加一件工具：**创建**（一次系统调用，加一块预留的栈）、**切换**（寄存器搬家，缓存变冷）、**内存**（常驻的少，预留的多），最后请 perf stat 把开销打印出来看。

## std::thread 背后，是一条内核线程

先站到操作系统的视角。在它眼里，进程和线程管的是两摊事：**进程是资源的容器**，地址空间、打开的文件、信号处理函数，装的全是进程的家当；**线程才是 CPU 调度的单位**。同一个进程里的多条线程共用那些家当，私产得各备一份——各自的栈、各自的寄存器、各自的程序计数器。共享与私有的分界画在哪儿，后面的同步故事就从哪儿长出来，那是第 2 章的正题。

那 `std::thread` 和内核线程是怎么搭上关系的？Linux 上的调用链是一层套一层的薄封装：`std::thread` 的构造函数调 `pthread_create()`，`pthread_create()` 底下是 `clone()` 系统调用，每一层干的都是替下一层备参数的活儿。

> 咱们立一张术语卡：**系统调用**。用户程序碰不了硬件、也建不了线程，想办这些事都得请内核出手，递交请求的口子就是系统调用。递交的动作本身要切换 CPU 的特权级，一来一回花的时间是纳秒到微秒级的。

`clone()` 可以当成 `fork()` 的精细控制版来理解：`fork()` 造出来的新进程什么都不共享，`clone()` 却允许调用的一方挑着共享——pthread 要的就是"共享地址空间、共享打开的文件描述符表、共享信号处理函数表"这一组。至于用户态线程与内核线程怎么对应，教科书里排了三种模型，您认个脸就好：

::: details 用户线程与内核线程的三种对应

| 模型 | 对应关系               | 长短                                             |
| ---- | ---------------------- | ------------------------------------------------ |
| 1:1  | 一条用户线程对一条内核线程 | 简单直接，创建与切换都要进内核                   |
| N:1  | 一堆用户线程挤一条内核线程 | 起线程便宜，一个阻塞全体瘫痪，多核用不上         |
| M:N  | 大量用户线程分到少数内核线程 | 轻量又能用多核，用户态调度器的实现最复杂         |

Linux 的 pthread 与 `std::thread` 用的是 1:1，其余两种是别的运行时的选择——Go 的 goroutine 就是 M:N 的当代招牌，咱们在第 6 章的协程里也会见到同一个思路：在一小撮线程上跑大量可挂起的任务。N:1 也不是纸上谈兵，Java 早年的 green threads 就是它的实例，后来官方撤掉了它，换成依托内核线程的路线；教训很明白——用户态调度器省下的创建钱，抵不过"一个阻塞就全体瘫痪"的险。

:::

眼下的地图上您只需要记一件事：**C++ 的 `std::thread` 在主流平台上都是 1:1，咱们每开一条，内核里就真的多一条，没有用户态的便宜可占。** 这也意味着线程的每次生死都要劳驾内核，用户态做不了主。

## 创建：一次系统调用，一块预留的栈

要开一条线程，库和内核要联手办的活儿不少。头一件就是进内核：`clone()` 是一次系统调用，用户态与内核态之间的一来一回本身就有成本。进了内核之后，内核得分配一份自己的线程档案（Linux 里它叫 `task_struct`，记着寄存器的快照、栈指针、调度信息、信号掩码，大小是几百字节到几 KB 的量级）、做初始化、把新线程挂进调度队列，这些活儿一样也省不掉。

第二件要办的是栈。`pthread_create` 默认不替您定大小，它去读调用线程的 `RLIMIT_STACK`，也就是 `ulimit -s` 看到的那个数。**多数发行版把它设成了 8 MB**，所以您量出来多半也是这个数——但它是发行版的设置，不是内核写死的常数，这一点不少旧资料讲浅了。

也别被 8 MB 吓着：那是虚拟地址空间里的**预留**，不是一口气占掉的物理内存。栈跟别的匿名内存一样按需落页——线程真的用到哪一页，内核才真的给哪一页，没碰过的部分只是地址空间里的一段空洞。所以开一条新线程，物理内存的增量远没有 8 MB。

> 咱们把术语卡立在这儿：**缺页**。线程摸到了还没落地的页，CPU 陷进内核，内核把物理内存补上再放行，缺页指的就是这一来一回。新线程的头几次函数调用、头几层局部变量，都会踩出这样的页来。
>
> 边栏：栈的尽头立着一页卫兵页（guard page），线程越了界，程序就干脆地崩给您看。崩在栈溢出上的版本算是走运的，静悄悄地越界写坏别人的数据才可怕。

那咱们把线程往多了开会怎样？`pthread_create` 不是总能成功的，失败时它返回错误码，最常见的那个叫 `EAGAIN`，意思就是资源暂时不够用。可能不够的地方有三处，程序起线程起不动的时候，您就往这张表上查：

::: details 三道闸门：EAGAIN 从哪儿来

| 闸门            | 管的范围             | 在哪儿看                          |
| --------------- | -------------------- | --------------------------------- |
| `RLIMIT_NPROC`  | 单个用户的进程与线程总数 | `ulimit -u`                       |
| `threads-max`   | 全系统的线程总数     | `/proc/sys/kernel/threads-max`    |
| `pid_max`       | PID 的总量           | `/proc/sys/kernel/pid_max`        |

```bash
ulimit -s                          # 栈的上限，多数发行版把它设成 8 MB
ulimit -u                          # 本用户的进程与线程数上限（RLIMIT_NPROC）
cat /proc/sys/kernel/threads-max   # 全系统的线程总数上限
cat /proc/sys/kernel/pid_max       # PID 的总量
```

几条命令花不了一分钟，您却把自己机器的闸门摸了一遍。具体的数字是多少不打紧，要紧的是您知道了闸门在哪儿。真要改线程栈的大小，`pthread_attr_setstacksize` 是正经的口子，这儿只留一个名字。

:::

### 掐一次表

光说贵不贵没意思，掐一回表就好了。配套代码仓里现成的基准就是给这件事备的：起一千个"只做一次加法"的空线程，一个一个地 join 收尾，拿总时间除以一千；同样的活儿再直接调用一千次当对照。

```bash
# 编译跑起来，数字随机器浮动，看量级就好
g++ -std=c++17 -O2 -Wall -Wextra -pedantic -pthread 00_os_threads_and_cost.cpp
./a.out 1000
```

```cpp
// 摘自代码仓的 00_os_threads_and_cost.cpp
const auto start = std::chrono::steady_clock::now();
long long sink = 0;
for (int i = 0; i < 1000; ++i) {
    std::thread t([i, &sink] { sink += noop_task(i); });  // 空任务：一次加法
    t.join();  // 做完就收，量的是"创建加收尾"的一整个来回
}
const auto stop = std::chrono::steady_clock::now();
// 对照组：同样的循环不起线程，直接累加，两版各除以 1000
```

两边的量级差多少，跑一遍就有数了：**直接调用是纳秒级的，起线程是微秒级的**，中间隔着的是实打实的数量级差距。sink 的校验也留了一手，两版算出的总数对不上就报错，防的是编译器把活儿优化没了。

> 边栏：计时咱们选了 `steady_clock`，因为它不受系统时间跳变的影响。wall clock 半夜里校时一跳的话，数据就废了。

笔者实测：WSL2 Arch Linux、内核 6.18、g++ 16.2.1、AMD Ryzen 7 9700X，命令照抄上面那行 `g++ -std=c++17 -O2 -Wall -Wextra -pedantic -pthread`，`./a.out 1000` 连跑三遍，数字都在同一量级：

```text
count = 1000（数字随机器与负载浮动，看量级就好）
threads : 88.5883 ms 总耗时，单次 88.5883 us
calls   : 0.00022 ms 总耗时，单次 0.22 ns
sink 校验一致：500500
```

三遍里 threads 的单次落在 75.8 到 88.6 us 之间，calls 稳在 0.21 到 0.22 ns。倍数约四十万倍——纳秒与微秒之间隔着三个数量级，这正是正文要您带走的那句话的实测版本。sink 一行两版同为 500500，活儿没被编译器优化掉。

> 边栏：这个数里其实混了 join 的等待、调度器的安排，还有循环自己的开销，量的并不是"纯创建"。测量其实从来不纯，您能把混进来的东西说清楚，数就有用了。

把这个量级放回任务粒度的语境里，卷首那条判据在这儿就落地了：**任务本身的计算量，应当显著贵过创建和调度它的开销。** 一次加法是纳秒级的活儿，配的却是微秒级的启动成本，给数组的每个元素开一个线程的写法就荒唐在这儿，得等两边的比例倒过来才划得来。

## 切换：寄存器搬家，缓存变冷

创建好了之后，真正反复发生的开销是切换。一个核在同一时刻里只跑一条线程（超线程的细分咱们暂且不管），下一个上场的轮到谁，由内核决定。

> 咱们把术语卡立在这儿：**上下文**。它指的是某一时刻 CPU 的全套状态：通用寄存器、程序计数器、栈指针，还有页表基址这样的关键寄存器。切换换的就是它。

换场的动作叫上下文切换：把当前线程的寄存器状态存回它的档案，再恢复下一条线程的寄存器状态，跳到它上回停下的位置接着跑。触发切换的原因不少，捡三样常见的说：时间片用完了要切，线程阻塞在 I/O 上要切，更急的线程到了也要切。

> 咱们把术语卡立在这儿：**时间片**。调度器分给每条线程的 CPU 时间是按小份发的，一份就叫一个时间片，用完了内核就考虑换人。它的长短由调度器按负载动态地定，并不存在写死的毫秒数。

对写程序的咱们来说，两行代码之间的任何一个位置都可能被切进去，您是预测不了的。[第 0 章 TSan 那篇](../ch00-concurrency-fundamentals/02-data-race-and-tsan.md)说的"并发 bug 难复现"，根子之一就在这儿：交错的窗口是调度器随手开的。

切换的**直接开销**是看得见的那部分：寄存器要一份一份地存好，再一份一份地恢复。x86-64 的通用寄存器有十六个，这部分算是小头。您可能会想，就算加上浮点与 SIMD 的状态，也不算多啊——咱们也承认不多，**贵的地方不在搬运上**。

贵的大头在**间接开销**，把镜头切到新线程这边：切换一回来，它面对的是一个刚刚还属于别人的世界。您可以把 TLB 想成页表的缓存，里头存着的映射多半是前一条线程的，得一条一条换掉；新线程自己的数据也大概率不在眼前这个核的缓存里，是冷的。缓存怎么分层、多核之间的一致性怎么维持，那是 [第 3 章](../ch03-atomic-memory-model/) 的正题，本篇只记一件事：**一次切换，会把您攒下的热乎劲儿冲掉一大截。**

切换还分同核与跨核两种，跨核的还要更贵一些：寄存器之外，又搭上了另一份冷的开销。perf stat 的输出里有一行 `cpu-migrations`，数的正是线程在核之间搬家的次数。

> 外部参考咱们只取量级：同一进程内两条线程之间的直接切换，公开实测大约是 1.2 到 1.5 微秒（把线程绑在固定核上的时候），不绑的时候大约 2.2 微秒。数字来自 Eli Bendersky 2018 年在一台 Haswell i7-4771 上的测量，方法透明而环境单一，跟您手头的机器没有直接关系，咱们只拿它定个量级。全卷的纪律也是这么立的：别人的数字进参考框，自己的数字自己测，本机的重测放在练习 3。

还有一样要想在前头：perf stat 数的切换是**次数**，不是单次的耗时，拿次数是乘不出时间来的。单次的耗时得靠专门的设计去量，练习 3 的乒乓法就是最小的一版。

笔者实测：WSL2 Arch Linux、内核 6.18、g++ 16.2.1、AMD Ryzen 7 9700X。乒乓法的最小实现是两条线程守一个 `std::atomic<int>`，一方看到自己的数就把球打回去，翻转一百万个来回（等待侧用 `yield()` 自旋），sink 累加接球次数防优化：

```text
rounds = 1000000, total = 0.41948 s, per-round = 419.48 ns (per-handoff = 209.74 ns)
sink = 1000000 (校验：应等于 rounds)
```

三遍的单回合都在 411 到 419 ns，折算一次交接约 205 到 210 ns。这个数比 Bendersky 的 1.2 到 2.2 微秒低了整整一个数量级，咱们得把原因说清楚，而不是假装对上了：Bendersky 量的是两条进程用管道**阻塞**收发的完整切换，睡与醒都得走内核；咱们这版是自旋等待，球多半在用户态就被接走了，量的更多是缓存行在两条线程之间搬家的延迟，而不是完整的睡眠加唤醒。它恰好从反面印证了正文的话——贵的从来不是寄存器搬运那一下。您想量贴近参考值的数，把自旋换成条件变量的阻塞等待再跑一遍，数字就会往微秒级靠。

## 内存足迹：一条线程占多大地方

内存那一头单独算。一条线程的常驻足迹里都有什么？`task_struct` 占几百字节到几 KB，栈是按需落页的、落了的页才算数，内核那边还有一份自己的内核栈，也是 KB 级。零零碎碎加起来，常驻的部分不算吓人。

> 边栏：内核栈与用户栈是两回事。内核栈是线程陷进内核办事时用的栈，它跟着线程走，不归咱们的代码直接碰；您只要记得一条线程在内核那边也有一份 KB 级的固定家当就好。

可**地址空间里的预留是真的**。按常见的 8 MB 算，一千条线程就是 8 GB 的预留，一万条就是 80 GB 的量级。64 位机器的地址空间倒是装得下，闸门却多半在半路就把您拦下了；就算闸门放行，切换的开销也早把收益吃光了。

您想亲眼看看也有办法，proc 文件系统把答案摊在那儿了：

```bash
# 换成您自己程序的 pid；Threads 那行数的是线程条数，VmRSS 数的是常驻内存
grep -E 'Threads|VmRSS' /proc/<pid>/status
```

起了十条线程再去看一眼，Threads 那行也就跟着变了：十条新线程加上主线程，数出来就是 11，这是咱们能直接观察到的"线程是真实物件"的证据。VmRSS 的涨落跟栈的落页连在一起，起的线程越多、摸到的页越多，它长得越大。这套观察随手就能做，也用不上特别的权限。

掂线程预算的次序也是同一套：**头一道看闸门，第二道看预留，末一道轮到的才是常驻。** 三道都过了关，才轮得到咱们谈线程数合不合理。

## 线程不是越多越好

切换什么时候发生，谁说了算？答案是：现代操作系统普遍用**抢占式调度**，时钟中断定期打断 CPU 的那一下，内核借机重新挑下一位上场的线程，不管当前的线程愿不愿意。

> 咱们把术语卡立在这儿：**抢占**。内核可以把正在跑的线程中途换下场，不必等它把手里的活儿干完，换场的时机由内核定。它跟协作式调度正好相反，协作式的写法得等线程自己交出 CPU。桌面与服务器上的主流系统都是抢占式的，所以咱们的程序随时可能被暂停或续上，时机不归咱们管。

调度器本身这些年一直在换代，Linux 的默认调度器就从 CFS 换成了 EEVDF（6.6 版内核起），老资料里写着旧名字的那一批，读的时候心里换算一下就好。调度器的门道咱们不展开，本篇要带走的事实只有一条：**谁上 CPU、跑多久、什么时候换人，决定权握在内核手里，而且随时会变。**

线程为什么不是越多越好？现在就能讲开了：核就那么几个，线程数远超核数的时候，切换变得频繁，CPU 的一部分时间花在了搬家上，真正干活的时间反而被挤掉。极端的例子第 0 章插过路标：一连接一条线程的 echo 服务，上万个连接对应的就是上万条线程，光切换和栈就够喝一壶的，正解是事件驱动或者协程的路线，那是 [第 6 章](../ch06-async-io-coroutine/) 的地盘。

所以工程上的常见做法是反过来的：**固定开一小撮线程，活儿排队送过去**，那就是 [第 5 章 的线程池](../ch05-future-task-threadpool/)；或者干脆用协程，把数量的压力挪到用户态里去。线程数的具体选法是第 5 章的正题，本篇只立下方向：**线程宁可少而常驻，也别开一大批来回切换。**

## perf stat：把开销打印出来看

开销聊了这么半天，给出的全是定性。把它们变成能看的数字，perf 是 Linux 上的正牌工具，本篇请您认识它最小的那一块：`perf stat`。它的用法摆出来您就明白了：

```bash
# 被测对象用配套仓里的基准（普通构建就好，perf 不与 sanitizer 版共用一个二进制）
perf stat ./os_threads_and_cost
```

跑完了以后，它会把一张小表打到您的终端上，咱们挑默认输出里最有用的四行来认：

| 输出行           | 它数的是什么                     |
| ---------------- | -------------------------------- |
| task-clock       | 这次运行占掉了多少 CPU 时间      |
| context-switches | 期间发生了多少次上下文切换       |
| cpu-migrations   | 线程在核心之间搬了多少次家       |
| page-faults      | 缺页次数，栈按需落页就计在这儿   |

默认输出里还有 `instructions` 与 `cycles` 一类的行，它们更贴近第 4 章的口味，本篇暂不碰；四行看熟了，别的行往后自然就认识了。

读法是**拿来对照**的。跑两个版本的程序，把这四行数字摆在一起看涨落：切换次数翻了几倍，缺页多了多少，开销的故事就从感觉变成了记录。四行恰好接住前面两节——创建一节说的按需落页对应 `page-faults`，切换一节说的搬家对应 `context-switches`，跨核的搬家记在 `cpu-migrations` 里。您要嫌一遍的数不稳，`perf stat -r 5` 会把基准连跑五遍，均值和波动就都交给您了；数字跳得厉害的机器上，判断也得跟着谦虚。

这一节的输出咱们给不出本机的真实数字：笔者这台 WSL2 里 perf 没有安装（`command -v perf` 为空），照卷里的纪律，编造一张表比没有表更糟。装法两条路：Arch 系是 `sudo pacman -S perf`，Ubuntu 系是 `sudo apt install linux-tools-common linux-tools-$(uname -r)`。装好之后 `perf stat ./os_threads_and_cost` 照正文跑，上表那四行就是您的机器自己交出来的数，拿它跟您起线程的次数对一对量级，这一节的手感就练到了。

一句实话也得说在明处：perf 不是哪儿都预装的，WSL2 里它常常缺席，装好了的环境也可能因为 `perf_event_paranoid` 的限制让一部分事件看不到。工具到不了的地方，咱们卷里的替代路线是 chrono 基准加 sanitizer：掐表的事归 chrono，看正确性的活儿归 TSan 与 ASan。

> 边栏：跟 sanitizer 的二进制别混着用，这是卷里的固定做法——TSan 版本自己在代码里插了簿记，拿 perf 去数它，数出来的多是工具自己的动静。要跑 perf，就用普通构建的二进制。

顺路再认两样工具：`perf top` 交互式地看当下的热点，`top -H` 看每条线程各自吃了多少 CPU，都不在本篇展开。采样的主课堂（`perf record` 与 `report`）在本章后面的无锁篇，伪共享（各写各的数据，却挤在同一个缓存行上）的现场重测也放在同一章里。

临走还登记一个名字：**futex**，Linux 上 mutex 的实现核心——无竞争的时候全在用户态办完，真有竞争了才进内核睡等。咱们提了一路的锁到现在还是黑盒，它的深讲在[第 2 章的同步原语工具箱](../ch02-mutex-condition-sync/06-sync-primitives-toolkit.md)。

## 本篇收进包里的东西

- `std::thread` 在主流平台是 1:1 模型，一条用户线程对一条内核调度实体，创建走 `clone()` 系统调用。
- 创建是微秒级的：一次系统调用、一份内核档案、一块按 `RLIMIT_STACK` 预留的栈（多数发行版设成 8 MB），按需落页。
- 切换也是微秒级的，寄存器搬运是小头，**TLB 与缓存变冷才是大头**。
- 线程数的闸门有三道：`RLIMIT_NPROC`、`threads-max`、`pid_max`，顶到了 `pthread_create` 就返回 `EAGAIN`。
- perf stat 的四行：`task-clock`、`context-switches`、`cpu-migrations`、`page-faults`，拿它们做对照，开销从感觉变成记录。
- futex 也登记在案：无竞争的加锁解锁全在用户态办完，进内核的才是慢路径，正源在第 2 章的工具箱。

咱们把三样开销也收成一张速查表，量级走的是定性口径：

| 开销             | 量级              | 在哪儿看                       |
| ---------------- | ----------------- | ------------------------------ |
| 创建（系统调用加栈） | 微秒级            | chrono 基准，练习 1            |
| 切换             | 微秒级            | perf stat 的 context-switches  |
| 常驻内存         | KB 级，预留是 MB 级 | /proc 的 status 页             |

## 练习

### 练习 1：给创建成本掐一次表

编译运行配套仓里的 `00_os_threads_and_cost.cpp`，记下两版的单次耗时与倍数，把数字填回本篇的占位里。然后把次数换成 100 与 10000 各跑一遍，看看量级是不是稳的。做完再想一步：起线程那一版里，除了创建本身，这个数还混进了什么？掐表一节的边栏点过名，把它们认出来。

有 perf 的机器上加做一步：拿 perf stat 跑同一个基准，把 `context-switches` 的数字跟您起的线程次数对一对，看看是不是同一量级。这一步练的是计数器与代码对得上号的手感。

报数的方式也讲究：把两版的数都记全，光留一个倍数是不够的。原始数留下了，往后换机器重跑才有得对。

### 练习 2：读一回 pthread_create 的手册

打开 man7.org 上的 `pthread_create(3)` 手册页（本机敲 `man pthread_create` 也一样），回答两个问题：默认栈大小是从哪个 limit 来的？返回 `EAGAIN` 的条件列了哪几条？然后把本机的 `ulimit -s`、`threads-max`、`pid_max` 都查一遍，跟手册里的条款对上号才算完。练的是查一手资料的手感，这比背博客可靠多了。

对答案时留意 ERRORS 一节的措辞：手册说的是**可能**的原因，不是必然的判决。哪一道闸门真顶到了，还得拿机器上的数字来认。

### 练习 3：乒乓法测切换

用两条线程和一个 `std::atomic<bool>` 就能搭起测切换的台子：线程 A 把旗子设成 true，等它变回 false 再走下一步，线程 B 做的正好是反过来的一半，往复一百万个回合。拿总时间除以回合数，单个回合的成本也就出来了，再拿它与本篇参考框里的数字对照量级。

做完再追问一句：这个数里混了哪些不属于切换本身的开销？atomic 的读写、循环的判断，全都混在里头了。您能说清混进来的都是什么，这个数就有用了。请把测完的数记到参考框旁边：同一台机器上，乒乓的每回合耗时与创建的耗时各自是多少，两者的比例本身就有讲头；机器换一轮之后再记一轮，比例是不是稳的，比单个的数更值得看。
