# 为什么并发：世界观与卷地图

跟您交个底：笔者到现在写并发代码，都比写别的代码多留一分小心。它没有一个像 RAII 或者移动语义那样清楚的边界，学会了就能划出一块自留地。并发是一整套看代码的眼光，咱们连读写本身都要重新掂量：这个值写进去以后，另一条执行流什么时候看得见？两个人同时去改同一处数据的话，又会发生什么？这样的疑问，在单线程的世界里压根不存在。

> 咱们把全卷最要紧的一句话放在最前头：程序写对了，快才真的有意义。

本篇是全卷的门面，咱们把几样要紧的东西一次摆齐：把并发与并行分清楚，把三条贯穿全卷的原则立起来，用 Amdahl 的算例掂一掂并行的收益上限，最后把整卷的地图摊开。您读完它，不一定能写出一行能跑的并发代码，但您会知道整条路长什么样、路口在哪儿、哪几段路要系好安全带。

## 单线程的世界，它好在哪里

您多半已经跟单线程代码相处了很久，那段日子确实是舒服的。函数调用的顺序就是执行顺序，变量读出来的值就是您刚写进去的值，一切都是说得清的。程序出了错，您拿调试器一路单步跟下去，哪一行出的错，答案也是确定的。复现这件事在单线程里几乎不成为问题：同样的输入，跑一百遍也就是一百遍同样的轨迹。

> 咱们的术语卡：**执行流**。本卷用它统称一条顺序执行的代码路径：OS 线程是执行流的一种，协程也是其中的一种，连信号处理函数的那一小段都算。它比线程这个词少了些偏向，咱们聊结构的时候多用它。

舒服的日子走到某一天，任务处理不过来了。咱们想象一台数据采集器：它要一边按毫秒读传感器，一边把攒下的数据往网络上送，还要时不时地刷新一块状态屏。单线程的写法，就是咱们把这三件事排进同一条循环里：

```text
while (运行中) {
    读一批传感器数据;          // 快，微秒级
    攒够一批就往网络上送;      // 慢，可能卡几百毫秒
    刷新状态屏;                // 快，但必须按节拍来
}
```

麻烦跟着就来了。往网络上送数据的那一步一阻塞，整条主循环就卡在了原地，屏幕也跟着冻住了，传感器更没人管了。您等网络超时回来，攒下的数据已经缺了一截，屏幕上画的还是几秒前的旧值。这类困境不是采集器独享的：桌面软件在网络请求期间整块界面失去响应，咱们都见过。服务器那边的情形也一样，一个客户端的慢连接要是把整个服务堵住，后面的请求就全都在排队了。

时钟走到了 2000 年代的中段，CPU 的主频提升碰上了功耗的墙，厂商把力气从单核的提速，转到了往芯片上多放几个核。今天的桌面 CPU 十几个核、服务器上百个核，也都不算稀奇了。硬件把并行执行的能力端上来了，咱们用不用得上、用得好不好，看的都是软件这一侧的并发功底。

您环顾一圈，能走的路看起来只有一条：再开一条执行流。走了这一步，要操心的事就换了一批。等两条执行流都跑起来了，共享的数据谁来保护？谁改了、谁读了、次序怎么算？出了错又怎么查？这些问题的答案，卷五会用三十篇正文慢慢交给您。

顺着说一句本卷的排法：头一篇为什么不是 `std::thread` 的 API 手册？因为 API 手册谁都翻得到，难的是把八章的次序排对。咱们把地图放在头一篇，往后每走到一章的时候，您都知道自己身在何处。

## 并发换来的两样东西

回到采集器的现场，咱们把并发换来的东西点一点。头一样的东西是关注点分离。采集、上报、刷屏本来就是三件逻辑上独立的事，硬挤在一条循环里的时候，谁的故障都要连坐别人。拆成三条各管各的执行流以后，每条流的代码都变简单了。改上报逻辑的时候，您也不必再惦记屏幕的刷新节拍，上报的重试与退避也不必再跟传感器的采样节奏纠缠。

这件事在单核机器上同样是成立的。时间片轮转会让它们轮流推进各自的活儿，光是结构上的清晰就已经很划算。这一点 Williams 在《C++ Concurrency in Action》的第一章里也是这么起头的：他讲线程的卖点，讲的就是把不同的职责交给不同的执行流，性能反而排在后头，这也是咱们全卷的排法。

另一样的东西是性能，它的来路有两条。头一条的来路是多核并行：把能分开的计算散到几个核上同时算，这是 ch04 往后的重头戏。另一条的来路就更朴素，咱们叫它重叠等待：等磁盘、等网络的时候，CPU 是闲着的，并发让咱们在等一份 I/O 的时候去推进别的活儿，单核的机器也能把这块空闲用起来。

采集器那个例子其实两条来路都沾边。上报阻塞的时候，采集与刷屏的活儿不该跟着陪葬，这用的是重叠等待。哪天数据量大到单个核算不过来了，咱们再谈把计算散开。两条来路对应着两类的手段，前者靠的是结构与调度，后者靠的是分块与负载，您往后会在不同的章里分别遇见它们。

## 并发与并行，两个常被混用的词

聊到并发和并行的时候，大家经常把它们换着用，在计算机科学里它们各有各的地盘。Rob Pike 在 2012 年的讲座 *Concurrency Is Not Parallelism* 里说过一段流传很广的话，咱们把原句抄过来：`Concurrency is about dealing with lots of things at once. Parallelism is about doing lots of things at once.` 同一组幻灯片里还有更短的一句：`Concurrency is about structure, parallelism is about execution.`

翻成中文的说法就是：并发说的是同时应对很多事情，并行说的是同时执行很多事情。两句话就差在了一个字上，差的却是着眼点。咱们把区分摆成一张表：

| 维度 | 并发 | 并行 |
|---|---|---|
| 关心什么 | 结构：把活儿拆成能交替推进的部分 | 执行：多个硬件单元在同一时刻真干活 |
| 需要多核吗 | 不需要，单核靠时间片轮转也能跑 | 需要，没有多个执行单元就无从谈起 |
| 谁来保证 | 咱们写的代码结构 | 操作系统调度与硬件 |
| C++ 里的表达 | `std::thread`、`std::async`、协程 | 同样的设施，只是跑在了多个核上 |

并发关心的是结构，把一个问题拆成多个能交替推进的部分，再用线程、协程、事件循环这样的机制去管理它们。并行关心的是执行，多个硬件单元在同一个时刻真真切切地各自干活，多核 CPU、多处理器、GPU 之类的硬件都算在这个行列里。咱们把区分落到硬件的层面，就看得更清楚了。

并发的运行不要求多核，咱们看单核的机器：它靠操作系统的时间片轮转，也就是把 CPU 切成一个个的小片、轮流发给各条线程，照样能跑出并发的效果，在宏观上看它们就像是同时在推进的。并行在没有多个执行单元的时候就无从谈起，要不然就没有核心替它干活了。

咱们顺手看一眼自己的机器：

```bash
nproc                            # 逻辑核心数
lscpu | grep -E 'Core|Socket'    # 每颗 CPU 的物理核数与插槽数
cat /proc/loadavg                # 最近 1/5/15 分钟的平均负载
```

几条命令花不了十秒，却能让后面的讨论落在您自己的机器上：您自己的机器上有几个核、负载高不高，往后聊时间片、聊粒度的时候，您都可以拿它来对照。

> 边栏：`nproc` 数出来的是逻辑核。开了超线程的机器，一条物理核对应的是两条逻辑核，并发的小任务是能沾光的，吃满计算型的并行任务却未必翻倍。数出来是几核其实不打紧，要紧的是您知道自己数的是什么。

这个区分为什么值得咱们花上小半节的篇幅？因为在 C++ 里，咱们手里的 `std::thread`、`std::async` 与协程，表达的都是并发这个结构。这些任务最终是挤在一个核上分时轮流地跑，还是散到不同的核心上真跑起来，取决于操作系统的调度和硬件的能力，不归咱们直接指挥。

咱们要负责的是另一件事：无论程序最终用上了几个核，它都得是对的。加速是正确性之上的一层收益，这样的次序倒不得。

咱们顺带把标准库的家底数一遍：`std::thread` 管的是 OS 线程，`std::mutex` 与它的守卫们管的是互斥，`std::atomic` 管的是原子与内存序，`std::future` 与 `std::promise` 管的是任务的结果，C++20 起又添了 `std::jthread` 与协程这两样新丁。这些名字您现在一个都不用记，卷五会一个一个地把它们请上台。

> 边栏：本篇从头到尾没有写一行真正的 C++ 线程代码，这不是咱们偷懒。`std::thread` 的 API、生命周期与 RAII 收尾，咱们把正源放在 [ch01 线程：第一条执行流](../ch01-thread-lifecycle-raii/)，本卷的纪律叫 `先用后教` 零容忍：一样东西还没讲过，正文就不会让您上手用它。您要是手痒，[下一篇](./02-data-race-and-tsan.md)咱们就动真格，亲手写出一段真的会出错的两线程代码。

## 三个常把人带偏的误区

往下走以前咱们还要点破三个常见的误区，它们都出自把并发与并行混为一谈的习惯。

头一个误区是把并发当成追求快的手段。并发换来的头一样东西其实是结构，快不快就得看瓶颈在哪儿了。咱们的采集器例子改成分流的写法，就算跑在单核的机器上也没有变慢，结构上的收益是白得的。不过反过来看，一个本身不慢的程序硬上并发的话，管理上的开销还可能倒贴，这笔收益的式子，咱们留到后面的 Amdahl 一节再交给您。

第二个误区是多线程一定用满了多核。八条线程挤在一个核上分时轮流地跑，那是并发而不是并行，吞吐可能连单线程的版本都比不过。至于有没有真的把多核用上，要看操作系统的调度，也要看程序有没有真的把计算分开。ch04 的 perf 会教咱们怎么把这件事量出来，光靠感觉是不作数的。

第三个误区是把协程当成提高并行度的手段。协程给的是并发的结构，它管的是怎么把大量等待着的活儿组织好，运行还是落在一小撮线程的身上。把协程当并行加速器来用的话，方向打根上就偏了，ch06 讲协程的时候咱们还会回头敲打这一句。

三个误区的病根是同一个：把结构与执行混成了团。咱们把结构立好，执行的事交给机器。

## 三条原则，立在卷首

接下来咱们把全卷会反复回指的三条原则正式立起来，您往后在每一章的篇首都会再见到它们。现在您把它们当口号读也没关系，每一条背后都站着几章的正文，等您走完一圈回头再看，它们就不再是口号了。

咱们为什么立的是三条而不是一条？因为它们把守的是三道不同的关卡：价值的次序、手段的次序、学习的次序。关卡各有各的样子，方向却指向了同一头。

| 原则 | 一句话为什么 | 落点 |
|---|---|---|
| `先正确性，再性能` | 错误的快是没有意义的 | ch00/02 数据竞争与 TSan 篇起，全卷 |
| `先锁，再无锁` | 无锁把正确性的门槛抬得更高 | [ch02 · 共享与同步](../ch02-mutex-condition-sync/) → [ch04 · 无锁与性能实测](../ch04-concurrent-data-structures/) |
| `先同步，再任务` | 任务层是盖在同步原语上头的 | [ch02 · 共享与同步](../ch02-mutex-condition-sync/) → [ch05 · 从线程到任务](../ch05-future-task-threadpool/)、[ch06 · 协程](../ch06-async-io-coroutine/) |

### 头一条：`先正确性，再性能`

一份跑得飞快但偶发错乱的并发代码，比一份慢一些但行为确定的代码糟糕得多，咱们全卷都按这个价值排序。原因藏在并发出错的形态里：data race，也就是两条执行流不加同步地读写同一处内存，这可是 C++ 标准里的未定义行为。它的下场可能是当场崩溃，也可能长久地看起来没事，却悄悄改坏了别处的数据，而且是极难复现的。

咱们把难复现这件事再往深里说一层。单线程的 bug，同样的输入多半能再跑出同样的错。并发的 bug 却依赖两条执行流恰好在某个微秒窗口里交错了，您加一条日志、换一台机器、甚至只是重新编译一次，窗口就挪走了，错也就跟着躲开了。多少团队的整夜加班，耗的就是这样的错。所以卷五的次序永远是：正确性验住了，咱们再谈快不快。

data race 的正式定义、TSan 这个抓竞态工具的第一课，就在紧跟着的下一篇，全卷的测量纪律也从那里开讲。咱们把话放在最前头：全卷任何一处性能取舍，您都会看到咱们把对错摆在快慢的前头，其实一次例外也没有。

至于正确性拿什么来验，卷五的答案是工具加压力：TSan 干的是抓竞态的活，断言核对着程序的不变量，压力测试把交错的窗口撑大了。下一篇起您就会一件一件用上它们。

### 第二条：`先锁，再无锁`

无锁编程的名字听起来更高级，实际上是把正确性的门槛抬得更高。内存序的讲究、内存回收的门道，还有 ABA 的难题（一个值从 A 改到 B 又改了回来，读它的人看不出中间动过），每一处都够单独地写上一章，到了 ch03 和 ch04 咱们再分别伺候。无锁代码的正确性论证，靠的是内存模型的严密推理，靠的可不是跑一万遍没崩。

锁在绝大多数的场景里够用，行为也经得起工具的核对。拿一把 `std::mutex` 配上 RAII 守卫的写法，临界区的里外都写得清清楚楚，咱们拿 TSan 与代码评审都看得明白。所以咱们的路线是：咱们用锁把程序写对，等实测真的指出了锁的瓶颈所在，再回头考虑无锁的事。

说到什么时候轮得到无锁，咱们只认一个信号：profile 的火焰图里，锁的等待占了显眼的一块，而且这段代码真的在关键路径上。两个条件都齐了，咱们再进 ch04 的门。

[ch02 共享与同步](../ch02-mutex-condition-sync/) 会一路把锁的知识从 mutex 讲到阻塞队列，[ch04 无锁与性能实测](../ch04-concurrent-data-structures/) 里才轮到无锁与 perf 的登场，次序就是这么排的，咱们全卷都照它走。倒着走的人也不是没有，他们的代码往往能跑，只是落得没人敢改的地步，连他们自己都不敢碰了。

### 第三条：`先同步，再任务`

直接管理线程是件细致的活儿。join（等线程收尾）的时机、参数的生命周期、取消怎么传播，处处都值得咱们操心。咱们到 [ch01 线程：第一条执行流](../ch01-thread-lifecycle-raii/) 里把基本功练扎实，往上的任务层才敢放手用：`std::async`、线程池、协程，把这些细活收进了库，让您面对的是一份份提交出去的活儿，而不是一条条要自己收尾的线程。

不过任务是盖在同步原语上头的。底下的 mutex、condition_variable（管的是让等待的线程在条件满足时醒来）不认识，上层的取舍也就无从谈起。线程池的关闭、future 的等待、协程的挂起与恢复，件件都要落到谁等谁、等什么、等多久的老问题上，这些问题的地基全在 ch02。[ch05 从线程到任务](../ch05-future-task-threadpool/) 和 [ch06 协程](../ch06-async-io-coroutine/) 讲的是上层，它们的料却都要从 ch02 取，这一层咱们想绕也绕不开。

分层的好处是节节可换：线程池的实现换了，提交任务的那段代码不用跟着动。同步原语稳定了，任务层才能放心地在上面盖楼。这也是咱们把 ch02 排在 ch05 前面的原因。

咱们见过的并发事故，相当一部分来自把这个次序倒了过来。

## Amdahl：串行占比压着加速的天花板

原则立完了，咱们来算一算收益。硬件翻了八倍，程序能快几倍？Amdahl 定律回答的就是这个问题。它的出身值得一提：Amdahl 在 1967 年的原论文里一个公式都没有，论文里其实只画了一张图，今天用的公式是后人从他的论证里整理出来的通行表述。IEEE SSCS News 在 2007 年重印这篇论文的时候，编者按倒是写得很直白：`it has no equations and only a single figure`。

咱们按通行表述把式子写出来，`S(N) = 1 / ((1 - f) + f / N)`，其中 S 指的是加速比，N 是处理器的个数，f 是程序里可以并行的那部分占比，剩下的 `1 - f` 就是只能串行的部分。

式子的脾气一眼就能看穿。串行的部分不管分给多少个核，都只能孤零零地自己跑，分母里的 `1 - f` 就永远蹲在那儿。当 N 趋向无穷大的时候，`f / N` 这一项就趋向了零，加速比也就摸到了自己的天花板 `1 / (1 - f)`。咱们把几组数字亲手代进去：

| 场景 | 代入 | 加速比 |
|---|---|---|
| 4 核，可并行 90% | `1 / (0.1 + 0.9/4)` | 3.08 倍 |
| 8 核，可并行 90% | `1 / (0.1 + 0.9/8)` | 4.71 倍 |
| 16 核，可并行 75% | `1 / (0.25 + 0.75/16)` | 3.37 倍 |
| 1024 核，可并行 90% | `1 / (0.1 + 0.9/1024)` | 9.91 倍 |

咱们把头一行的算法念出声：分母的 `0.1 + 0.9/4` 算出来是 `0.325`，它的倒数就是 3.08。每一行的算术都是这个长度，您在纸上两分钟就能全部复验完，这些是纯数学的推演，不牵扯任何一台真实的机器。最扎眼的是末一行：一千零二十四个核的机器，九成的代码都能并行，换来的加速还不到十倍。串行的那 10%，就这么把千核的雄心摁在了个位数上。

天花板本身的几个取值也值得看一眼，咱们单独列一张表：

| 可并行比例 f | 渐近上限 `1 / (1 - f)` |
|---|---|
| 50% | 2 倍 |
| 75% | 4 倍 |
| 90% | 10 倍 |
| 95% | 20 倍 |

咱们还可以换个方向问：f 取 0.9 的时候，想摸到上限的 95%（也就是 9.5 倍），咱们得堆上多少个核？解开 `1 / (0.1 + 0.9/N) = 9.5` 这个方程，得到的答案约是 171 个。咱们从 16 核加到 171 核，硬件翻了十倍还多，却始终差了那一口气。

Amdahl 本人在论文里也是不留情面的，咱们引一段原文：`A fairly obvious conclusion which can be drawn at this point is that the effort expended on achieving high parallel processing rates is wasted unless it is accompanied by achievements in sequential processing rates of very nearly the same magnitude.` 他的意思是，并行的投入要是没有差不多同量级的串行改进陪着，那就白费了。

他还给开销的影响估过一句：`Overhead alone would then place an upper limit on throughput of five to seven times`，光开销就能把吞吐摁在五到七倍的范围内。咱们看他的立场，从论文的标题里就看得出来：单处理器的路线要是走不通，光靠堆并行的核数是救不回来的。

有人把 Amdahl 读成了多核无用论，那是读拧了。它真正要说的，是串行部分的改造同样要紧：您想把 16 核用出 8 倍的加速，光把并行部分做满是不够的，就算可并行的占到了九成，16 核也只出得了 6.4 倍，串行的那一成还得接着瘦，瘦到 7% 以下才算够着了 8 倍。

### Gustafson：换个问法，把题做大

在咱们看来 Amdahl 显得悲观，因为它默认问题的规模不变：核多了，还是解同样大的题。1988 年 Gustafson 换了个视角：现实中的人们拿到更多算力，往往掉头去解更大的题，让并行部分的活儿随核数线性膨胀，串行的部分留在原地不动。这个口径下的加速比写成 `S(N) = α + (1 - α) · N`，α 指的是串行占比。

咱们同样在 16 核的机器上、α 取 0.1 的时候看这个式子，它给出的数是 14.5 倍，一下子乐观起来了。α 取 0.25 的时候，同一个式子给的是 12.25 倍，串行的占比一升，乐观的成色也就跟着降了。

两个定律其实并不打架，它们回答的是两个问题，咱们对照着看：

| 问法 | 定律 | 口径 |
|---|---|---|
| 同一批活儿能快多少 | Amdahl | 问题规模固定，串行占比拖后腿 |
| 同样的时间里能多干多少活儿 | Gustafson | 问题规模随核数长大 |

做工程的时候，您得知道自己想问的是哪一个。

还有一句口径要交代：本节的所有数字都是理论推演，跟任何真实程序的实测加速比都不挨着。f 的来路，正路走的是 profile：咱们去测串行版的各段耗时，再算一算可并行的部分占几成。头一次估糙了也不要紧，做完了一版咱们再回头修它，Amdahl 的数字是活的预算。而实测有自己的章法，数字得带上环境、命令与复现的路径，那套咱们到 ch04 的 perf 课堂再立。

> 边栏：别拿本节的数字去对标任何实测。理论值画的是天花板，实测的数还压着调度、缓存、同步这些真实的重量，两边走的不是一个口径。全卷的正文里，凡是真刀真枪的性能数字，您都会看到它带着可复现的命令，或者干脆挂着待回填的占位。

## 快与多的取舍

### 吞吐与延迟，常常对着干

说完了加速比，咱们再看一对经常打架的指标：吞吐量与延迟。吞吐量是单位时间完成的任务总数，延迟是单个任务从提交到完成的时间。两个数咱们都想让它变大，方向却常常是相反的，咱们拿批处理当最直观的例子。

任务来了就马上处理，每个任务的延迟最低。可咱们把任务攒成一批再处理，批内能合并的操作多了，总吞吐上去了，排在队尾的任务却得多等攒批的这一整段时间。数据库的批量提交、日志的攒批、网络的收发，处处都有这样的选择题。批越大的时候吞吐越漂亮，队尾排着的任务就等得越冤了。

队列的深度也是同款的一个旋钮。队列放得深的时候，突发来了接得住，吞吐也就平稳了，可队列深了以后，排进来的任务等待的时间也就长了。日志的队列、网络的收包、线程池的任务箱，咱们处处都在拧这个旋钮，拧到多大的问题，并没有放之四海皆准的答案，只有您业务的延迟预算说了算。

负载均衡里也有同款的取舍。挑最短队列的调度能把平均延迟压低，调度本身的开销却比简单的轮转更高。哪个更要紧并没有标准的答案，交易系统追求的是延迟，数据管道追求的是吞吐，多数服务是在一段可以接受的延迟里把吞吐做大。真到动手设计的时候，您得把自己的答案想清楚，再把答案写成代码里看得见的参数。

平均值有时候是会骗人的。排队论里有一条老的观察：当系统真的贴近了满载，排队等待的波动会陡然放大，延迟的长尾也就翘了起来。所以对延迟敏感的服务，行话看的往往是 P99 这样的分位数，平均值反而落在了后头：平均值看着倒是体面，一百个请求里最难堪的几个，恰恰是用户记得最牢的。量法的深究归 ch04，咱们本篇只把名字交代下来。

### 任务粒度：拆多细才划算

咱们要练的另一门判断力是任务粒度，也就是把活儿拆成多大的单元交给并发。拆得太细的时候，管理费会吃掉收益的大头。线程的创建与销毁、上下文切换（线程换入换出的那一下）、锁的进出，每一样都要吃 CPU 的时间。任务本身的计算量要是比这些开销还小，并发反而把程序拖慢了。

咱们走个极端就好懂了：给数组的每个元素开一个线程去做一次加法，管理线程的成本能是那次加法的成百上千倍。Williams 在《C++ Concurrency in Action》的第一章里给过定性的一句：`If the task being run on the thread is completed quickly, the actual time taken by the task may be dwarfed by the overhead of launching the thread…` 翻成中文的意思是：任务三两下就跑完了，起线程的功夫反而成了大头。

那么粒度有没有一个能背下来的数字门槛？咱们诚实地回答：没有公认的定值，旧资料里流传的十倍说法查无出处，咱们这卷不采信它。咱们只立定性的要求：任务的计算量，应当显著高于创建和调度它的开销。至于您自己的机器上起一个空线程要花多少微秒，[OS 线程与开销](./03-os-threads-and-cost.md) 那一篇会现场量给您看，咱们在本篇不预写任何数字。

<!-- 实验回填：空任务线程与直接调用的 chrono 对比，单次线程创建成本的量级（ch00/03 统一实验后回填） -->

拆粗了也有代价：剩下一堆的核看着一个线程忙，剩下的算力白闲着。工程上的做法是从较粗的粒度起步、测量、再试着细化，每一步咱们都拿数据说话。这其实就是头一条原则落在性能上的样子：没有测量的调优，咱们一概不认。咱们把粗细的取舍也摆成一张表：

| 粒度 | 长相 | 风险 |
|---|---|---|
| 太细 | 一个元素一个任务 | 管理费吃掉收益的大头 |
| 太粗 | 一条线程包圆全部的活 | 核闲着，加速上不去 |
| 合身 | 每个任务显著贵过调度的开销 | 收益与开销的两头都稳 |

数据怎么分块也有它的讲究：等分地切、按缓存行对齐地切、按负载动态地偷活儿，ch01 的 `parallel_for_each` 会带您走第一遍，更深的玩法在 ch04。

> 边栏：合身的粒度是量出来的，不是拍脑袋想出来的。在同一台机器上跑计算的任务与跑 I/O 的任务，合身的粒度能差出一个数量级，所以咱们把测量的纪律看得比口诀重。

## 什么时候不该用并发

讲了这么多为什么要用，咱们也得知道什么时候不用。头一类是 CPU 密集又没法分开的单任务，比如一段前后依赖缠在一起的纯数值计算，多线程是帮不上忙的，硬拆还要赔上同步的开销。递推的式子、迭代求解的循环、链式的变换，都是这一类的常客，它们的下一步要用到上一步的结果，天然就是串行的。

第二类是已经够快的程序，延迟远低于业务的阈值，这时引入并发换来的复杂度不值当。用不上的复杂度，每天都在给咱们增加维护负担。第三类是对确定性要求严苛的场合，某些控制系统要求每次响应都落在一个可预测的窗口里，多线程带来的调度抖动可能根本没法接受，嵌入式里这样的约束并不少见。

> 边栏：硬实时走的是另一套路子，正确性讲的是时间上限的保证，与本卷事后测量的章法是两套口径。咱们不在本卷展开，只提醒您别把两边的尺子混着用。

还有一类藏在了深处：您需要的其实是异步 I/O，而不是并行计算。咱们想象一个网络服务，它要同时伺候的连接成千上万，要是一连接一条线程地开下去，线程的数量本身就会成为瓶颈。这类场景的正解是事件驱动或者协程，用少量的线程配上 I/O 多路复用去管住大量的连接，那是 [ch06 协程](../ch06-async-io-coroutine/) 的地盘，咱们在本篇只把路标插在这儿。

咱们把上面的判断收敛成四问，四问里有一问答不上来的话，就该缓一缓了：

- 瓶颈是真的吗？拿数据说话，别拿感觉说话。
- 串行的部分占几成？串行占比太高，多核救不了它。
- 并发版的行为能验证吗？工具、断言、压力测试，至少备上两样。
- 团队接得住这份复杂度吗？写出来只是一半，养得住才算数。

末了咱们说句朴素的话：并发引入的复杂度是真的。data race、死锁（两条线程互相等对方手中的锁）、条件变量的虚假唤醒（没人叫它也会醒）、对象的生命周期，每一个都是难复现、难调试的主。单线程能解决的问题，咱们不要为了炫技上并发。并发的正当理由只有一条：单线程真的不够用了。

## 练习

### 练习 1：亲手算一次 Amdahl

设一段程序 80% 的工作可以并行，对应到公式里的写法就是 f 取 0.8。请您算出 8 核下的加速比与理论上限，再把 N 换成 1024 看看数字的脸色。最后的一问：想让上限翻上一倍的话，串行占比得压到多少？拿计算器就够了，三行算式的事。算完请您再写一小段：上头两组数字，对您手头某个真实项目意味着什么。

### 练习 2：三道判断题

请您判断对错，并各用一句话讲出您的理由，理由都得从并发与并行的区分出发：

- 单核机器上，写并发程序没有意义。
- 并行程序一定也是并发程序。
- 协程能提高单核机器的并行度。

给您的提示是：第二条不妨想想 SIMD 这样的数据并行，第三条想想协程到底给了您哪一样东西。判完您要是拿不准，就把三个误区的那一段回头再读一遍，答案其实都在里头。

### 练习 3：给四个场景开方子

下面的四个场景，哪些是值得引入并发的？该用什么样的形态？请您各写一两句判断，再对照本篇的口径：

- 一段前后依赖缠死的浮点计算，单线程跑的时间已经在可接受范围内。
- 一台采集器，读传感器、上报网络、刷新屏幕，任何一步阻塞都会拖住另外两步。
- 一个 echo 服务，要同时伺候上万个 TCP 连接。
- 一万张图片的批量缩放，图片之间毫无依赖。

第三条的路标本篇插过，您想想它指向的是哪一章再落笔。第四条请您顺手把数据怎么分块也写一句，分块的话数与图片总数的比例怎么定，练的正是任务粒度那一段的本事。
