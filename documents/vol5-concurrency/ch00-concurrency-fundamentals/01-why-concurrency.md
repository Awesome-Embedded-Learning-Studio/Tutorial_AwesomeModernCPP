# 为什么并发：一次阻塞引出的问题

嘿，欢迎来到并发。笔者先把话撂在这儿：一个具备规模和严肃性的项目，迟早要跟并发打交道。今天的桌面 CPU 十几个核、服务器上百个核都不算稀奇，您把代码全丢在一个逻辑核上跑，剩下的算力就白买了。

不过先别急着把整个工程改成"高并发"。比起争论并发到底能不能提速，笔者更想先提醒您一件事：**并发不好写，而且它换来的头一样东西并不是快。** 这一篇咱们不写一行线程代码，只把三个问题讲清楚：什么时候非上并发不可，并发与并行到底差在哪儿，以及这一卷打算怎么带您走。

## 单线程的世界，它好在哪里

您多半已经跟单线程代码相处了很久，那段日子确实是舒服的。函数调用的顺序就是执行顺序，变量读出来的值就是您上一次写进去的值，一切都是说得清的。程序出了错，您拿调试器一路单步跟下去，哪一行出的错，答案也是确定的。复现这件事在单线程里几乎不成为问题：同样的输入，跑一百遍也就是一百遍同样的轨迹。

> 这里小小的插个嘴：**执行流**，您可以认为他是一条顺序执行的代码路径。OS 线程是执行流的一种，协程也是其中的一种，连信号处理函数的那一小段都算——后两样您现在没听过不要紧，先记住头一句就够了。**执行流是一条顺序执行的代码路径**

舒服的日子总有个头。咱们想象一台数据采集器：它要一边按毫秒读传感器，一边把攒下的数据往网络上送，还要时不时地刷新一块状态屏。单线程的写法，就是把这三件事排进同一条循环里：

```text
while (运行中) {
    读一批传感器数据;           // 快，微秒级
    攒够一批就往网络上送;       // 慢，可能卡几百毫秒
    刷新状态屏;                // 快，但必须按节拍来
}
```

坏事了，咱们往网络上送数据的那一步**一阻塞**（卡在那儿等对方回应，等不到就一步不走），**整条主循环**就卡在了原地，屏幕跟着冻住，传感器也没人管了。等网络超时回来，攒下的数据已经缺了一截，屏幕上画的还是几秒前的旧值。

> 咱们再立一张术语卡：**阻塞**。一段代码发起了一个要等外部结果的操作，在结果回来以前它自己一步也走不了，这段状态就叫阻塞。等磁盘、等网络、等另一条执行流，都会让咱们阻塞。

这类困境不是嵌入式的采集器独享的，一些桌面软件在网络请求期间整块界面失去响应，咱们都见过。服务器那边也一样，一个客户端的慢连接要是把整个服务堵住，后面的请求就全在排队了。症结说穿了很朴素：**采集、上报、刷屏本是可以各干各的三件事，硬挤在一条循环里，最慢的那件就把其余的全堵住了。**

## 硬件那边，风也变了

就在这些年，硬件侧也在换挡。2000 年代的中段，CPU 的主频提升碰上了功耗的墙，厂商把力气从"把单个核做快"转到了"往芯片上多放几个核"。硬件把并行执行的能力端上来了，能不能用上、用得好不好，看的都是软件这一侧的并发功底。

回到咱们手头的活儿：模块要提速、多核要喂饱、阻塞要解开，环顾一圈，能走的路其实就一条——把这几件事拆开，再开几条执行流分头去干。

这么一拆，好处是立等可取的，咱们点一点。头一样是**关注点分离**：采集、上报、刷屏本来就是三件逻辑上独立的事，拆成三条各管各的执行流以后，每条流的代码都变简单了。改上报逻辑的时候，您不必再惦记屏幕的刷新节拍，上报的重试与退避（失败了隔一会儿再试，越失败隔得越久）也不必再跟传感器的采样节奏纠缠。这一点在单核机器上同样成立，光是结构上的清晰就已经很划算。

另一样是**性能**，它的来路有两条。一条是多核并行：把能分开的计算散到几个核上同时算，这是后几章的重头戏。另一条更朴素，咱们叫它**重叠等待**：等磁盘、等网络的时候 CPU 是闲着的，并发让咱们在等一份 I/O 的时候去推进别的活儿，单核机器也能把这块空闲用起来。采集器那个例子其实两条来路都沾边：上报阻塞的时候，采集与刷屏不该跟着陪葬，这用的是重叠等待；哪天数据量大到单个核算不过来了，咱们再谈把计算散开。

Williams 在《C++ Concurrency in Action》的第一章里也是这么起头的：他讲线程的卖点，讲的就是把不同的职责交给不同的执行流，性能反而排在后头。这也是咱们全卷的排法。

天下没有白来的收益。等两条执行流真跑起来了，问题就换了一批：共享的数据谁来保护？谁改了、谁读了、次序怎么算？出了错又怎么查？这些问题的答案，就是后面八章的正文。

## 并发与并行，两个常被混用的词

往下走以前，咱们得先把两个被大家用混的词分清楚。这两个词要是含糊着，后面每一句"多核有没有用上""协程到底加不加速"的讨论都会跟着含糊。

Rob Pike 在 2012 年的讲座 *Concurrency Is Not Parallelism* 里说过一段流传很广的话，咱们把原句抄过来：

> `Concurrency is about dealing with lots of things at once. Parallelism is about doing lots of things at once.`

翻成中文就是：并发说的是同时**应对**很多事情，并行说的是同时**执行**很多事情。同一组幻灯片里还有更短的一句：`Concurrency is about structure, parallelism is about execution.`——并发关心结构，并行关心执行。两句话就差在一个字上，差的却是着眼点。

**并发关心结构**：把一个问题拆成多个能交替推进的部分，再用线程、协程、事件循环这样的机制去管理它们（后两样是第 6 章才出场的新面孔，现在当名字听过就行）。并发不要求多核，一个 CPU 也能并发（如果您真是求学，可以考虑专攻操作系统和计算机组成体系，那边会有更加严密的答案回答您一个CPU凭什么也能并发）。

**并行关心执行**：多个硬件单元在同一个时刻真真切切地各自干活，多核 CPU、多处理器、GPU 都算。没有多个执行单元，并行就无从谈起。**因为总得有核心替它干活**。

咱们顺手看一眼自己的机器：

```bash
nproc                            # 逻辑核心数
lscpu | grep -E 'Core|Socket'    # 每颗 CPU 的物理核数与插槽数
cat /proc/loadavg                # 最近 1/5/15 分钟的平均负载
```

几条命令花不了十秒，却能让后面的讨论落在您自己的机器上。

> 边栏：`nproc` 数出来的是逻辑核。开了超线程的机器，一条物理核对应两条逻辑核，并发的小任务是能沾光的，吃满计算型的并行任务却未必翻倍。数出来是几核其实不打紧，要紧的是您知道自己数的是什么。

为什么这个区分值得花小半节篇幅？因为在 C++ 里，咱们手里的 `std::thread`、`std::async` 与协程，表达的都是**并发**这个结构。这些任务最终是挤在一个核上分时轮流跑，还是散到不同核心上真跑起来，取决于操作系统的调度和硬件的能力，不归咱们直接指挥。咱们要负责的是另一件事：**无论程序最终用上了几个核，它都得是对的。** 加速是正确性之上的一层收益，这个次序倒不得。

至于标准库里有哪些家当，您往后会一件一件亲自上手，眼下不用背名字。

## 那，是不是并发了，程序就一定受到极大的优化？

孩子们，没有免费的午餐，**并发可能有性价比，也有可能没有，甚至倒贴钱也不是不行！**

为了让大伙先有个感觉，我们做一个假设，假设我们的硬件核心翻了八倍，程序能快几倍？

有个 Amdahl 定律回答的就是这个问题。设程序里可以并行的部分占比为 `f`，剩下的 `1 - f` 只能串行，用 `N` 个处理器时理论加速比是：

`S(N) = 1 / ((1 - f) + f / N)`

这个式子的脾气一眼能看穿：串行的部分不管分给多少个核，都只能孤零零地自己跑，分母里的 `1 - f` 永远蹲在那儿。当 `N` 趋向无穷，`f / N` 趋向零，加速比就摸到了天花板 `1 / (1 - f)`。咱们代几组数字进去：

| 场景                | 代入                   | 加速比  |
| ------------------- | ---------------------- | ------- |
| 4 核，可并行 90%    | `1 / (0.1 + 0.9/4)`    | 3.08 倍 |
| 8 核，可并行 90%    | `1 / (0.1 + 0.9/8)`    | 4.71 倍 |
| 16 核，可并行 75%   | `1 / (0.25 + 0.75/16)` | 3.37 倍 |
| 1024 核，可并行 90% | `1 / (0.1 + 0.9/1024)` | 9.91 倍 |

最扎眼的是末一行：一千零二十四个核的机器、九成的代码都能并行，换来的加速还不到十倍。串行的那 10%，就这么把千核的雄心摁在了个位数上。

> 边栏：这一节的数字全是纯数学推演，跟任何真实程序的实测加速比都不挨着。它画的是天花板，实测的数还压着调度、缓存、同步这些真实的重量。所以甚至不光没有加速，反而性能还倒回去了！这就是笔者说的：**做工程的时候，`f` 的正路是拿 profile（性能剖析：测出程序各段各花了多少时间）去测串行版的各段耗时，头一次估糙了不要紧，做完一版再回头修**。
>
> 至于有人把 Amdahl 读成了"多核无用论"，那是读拧了。建议回去重新学习并发编程。它真正要说的，是**串行部分的改造同样要紧**：想把 16 核用出 8 倍的加速，光把并行部分做满是不够的，就算可并行的占到九成，16 核也只出得了 6.4 倍，串行的那一成还得接着瘦。

## 什么时候不该用并发

上面我们废了不少口舌，其实就是想暗示您这个问题的答案。

第一类就是 **CPU 密集又没法分开**的单任务，比如一段前后依赖缠在一起的纯数值计算。递推的式子、迭代求解的循环、链式的变换，下一步要用上一步的结果，**天然就是串行的**，多线程帮不上忙，硬拆还要赔上同步的开销。第二类是**已经够快**的程序，延迟远低于业务阈值，这时引入并发换来的复杂度不值当。第三类是**对确定性要求严苛**的场合，某些控制系统要求每次响应都落在一个可预测的窗口里，多线程带来的调度抖动可能根本没法接受，嵌入式里这样的约束并不少见。

换而言之，如果您在处理这些程序的执行速度层次的性能优化，您可以直接跳过去了，**别想**：本来只能顺序执行的，没性价比的，和就是要求实时性的（非嵌入式的朋友别管这个，嵌入式的朋友留一下RTOS的使用即可。）

> 有并发高手嘛？笔者想对这些朋友们分享一下自己的看法。其实还有一类，就是极端多的 IO 任务并发，也不要用传统的线程并发，而是事件驱动或者协程，用少量线程配上 I/O 多路复用（即，让一个线程同时盯着一堆连接，哪个就绪了就伺候哪个）去管住大量连接，那是 [第 6 章 协程](../ch06-async-io-coroutine/) 的地盘，这里只插个路标。
