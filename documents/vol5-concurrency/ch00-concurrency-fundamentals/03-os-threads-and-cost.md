# OS 线程与开销

咱们在 [data race 与 TSan](./02-data-race-and-tsan.md) 那篇里，把全卷的第一件工具收进了包里。这一篇咱们换个方向，往机器的那一边走一层：您写下 `std::thread t(func)` 的时候，操作系统那边发生了什么，又花掉了什么。

[头一篇](./01-why-concurrency.md) 聊任务粒度的时候，咱们留过一句话，说空线程的成本是要用微秒来计的。本篇就把那个数现场量给您看。

[为什么并发：世界观与卷地图](./01-why-concurrency.md) 里立下的三条原则，头一条讲的就是 `先正确性，再性能`。本篇聊的东西全在性能这一侧，正好用上它的后半句：程序对了，咱们才有资格谈它贵不贵。

数字的讲法照卷首的约定作数：占位没填上的时候，那句话咱们就当没说过。

还有一样东西也得摆在桌面上：开销的数字没有放之四海的定值，机器、内核版本、当时的负载，掺进来的每一手都不一样。所以数表咱们是不背的，本篇交给您的是一套往自己机器上量数的办法。

今天的路线也预告给您，咱们走三站加一件工具：

- 创建：一次系统调用，加一块预留的栈。
- 切换：寄存器搬家，缓存变冷。
- 内存：常驻的少，预留的多。
- perf stat：把开销打印出来看。

您把三站一工具走完，对开线程这件事的价钱就有数了。咱们把工具的接续也交代一句：ch00/02 的 TSan 在本篇不登场，它管的是对错，本篇管的是贵贱，两件事的尺子不一样。

## std::thread 背后，是一条内核线程

咱们从操作系统的视角看起。进程与线程在它眼里管的是两摊事：进程是资源的容器，地址空间、打开的文件、信号处理函数，装的全是进程的家当，线程才是 CPU 调度的单位。

同一个进程里的多条线程共用那些家当，私产倒是得各备一份，也就是各自的栈、各自的寄存器、各自的程序计数器。共享与私有的分界画在哪儿，后面的同步故事就从哪儿长出来，咱们到 ch02 再正式收拾。

本篇您只需要认下一件事：线程在内核的眼里，是一个独立的调度实体，它有自己的身份，也有自己的档案。

档案是内核建的，Linux 里它的名字叫 task_struct。寄存器的快照、栈指针、调度信息、信号掩码，全都记在里头了。档案本身不算大：大小也就是几百字节到几 KB 的量级，咱们把这个数记下来，等一下算内存足迹的时候要用它。

那 `std::thread` 和它们又是怎么搭上关系的？Linux 上的调用链是一层套一层的薄封装：`std::thread` 的构造函数调 `pthread_create()`，`pthread_create()` 的底下是 `clone()` 系统调用。咱们一路追下去，每一层干的都是替下一层备参数的活儿。

> 咱们在这儿立一张术语卡：**系统调用**。用户程序碰不了硬件、也建不了线程，想办这些事的时候都得请内核出手，递交请求的口子就是系统调用。递交的动作本身要切换 CPU 的特权级，一来一回花的时间是纳秒到微秒级的。它是用户态与内核态之间唯一的正经通道，本篇的清单上它还要出现好几次。

clone 可以当成 fork 的精细控制版去理解。fork 造出来的新进程什么都不共享，clone 却允许调用的一方挑着共享，pthread 要的就是其中一组，咱们把常用的三个名字点出来了：

| 标志 | 共享的东西 |
|---|---|
| CLONE_VM | 地址空间（代码、数据、堆都在里头） |
| CLONE_FILES | 打开着的文件描述符表 |
| CLONE_SIGHAND | 信号处理函数的表 |

这套东西的历史并不算长。早期的 Linux 内核只认识进程，线程的现代实现是 2.6 版起由 NPTL（Native POSIX Thread Library）定型的，它的设计文档挂在参考资源里，您感兴趣可以去翻一翻。

用户态线程与内核线程怎么对应，教科书里的排法有三种，咱们列一张表：

| 模型 | 对应关系 | 长短 |
|---|---|---|
| 1:1 | 一条用户线程对一条内核线程 | 简单直接，创建与切换都要进内核 |
| N:1 | 一堆用户线程挤一条内核线程 | 起线程便宜，一个阻塞全体瘫痪，多核用不上 |
| M:N | 大量用户线程分到少数内核线程 | 轻量又能用多核，用户态调度器的实现最复杂 |

Linux 的 pthread 与 `std::thread` 用的就是 1:1，其余两种是别的运行时的选择。Go 的 goroutine 是 M:N 的当代招牌，咱们在卷里也会遇见它的回声：[ch06 的协程](../ch06-async-io-coroutine/01-coroutine-basics.md) 也是同一个思路，在一小撮线程上跑大量的可挂起任务。

> 边栏：N:1 也不是纸上谈兵的排法，Java 早年的 green threads 就是它的实例，后来官方实现撤掉了它，换成了依托内核线程的路线。教训咱们也看得明白：用户态的调度器省下的创建钱，抵不过一个阻塞就全体瘫痪的险。

眼下的地图上您只需要记一件事：C++ 的 `std::thread` 在主流平台上都是 1:1，咱们每开一条，内核里就真的多一条，没有用户态的便宜可占。

1:1 的代价，咱们现在能看清一半了：线程的每次生死都要劳驾内核，用户态做不了主。另一半的代价藏在切换里，咱们把它往后面放一放。既然咱们每开一条都要进一次内核，那咱们就跟着进一趟，看看这回的钱都花在哪儿。

## 创建：一次系统调用，一块预留的栈

咱们要开一条线程的时候，库和内核要联手办的活儿不少。头一件要办的就是进内核：clone 是一次系统调用，用户态与内核态之间的一来一回本身就有成本。

咱们进了内核之后，要办的活儿也不止一桩：内核得分配 task_struct、做初始化、把新线程挂进它的调度队列，这些活儿是一样也省不掉的。它们加在一起的量级，就是后面掐表要量的东西。

### 栈从哪儿来

第二件要办的是栈。pthread_create 默认不替您定大小，它去读调用线程的 RLIMIT_STACK，也就是 `ulimit -s` 看到的那个数。

栈的数额值得咱们多说两句，因为不少旧资料把它写成了 Linux 默认 8 MB 的说法，那个说法把机制讲浅了。

咱们把真正的机制摆出来：默认栈大小取自调用线程的 RLIMIT_STACK，多数发行版把它设成了 8 MB，所以您量出来多半也是这个数，但它是发行版的设置，不是内核写死的常数。

手册里的另一个边角，咱们也给您提一句：RLIMIT_STACK 要是被设成了 unlimited，pthread_create 就改用各架构自己的定值，手册的原话是 `2 MB on most architectures; 4 MB on POWER and Sparc-64`。

> 边栏：栈的尽头还立着一页卫兵页（guard page），线程越了界，程序就干脆地崩给您看。崩在栈溢出上的版本算是走运的，静悄悄地越界写坏别人的数据才是可怕的。

> 边栏：跟着 RLIMIT_STACK 走的设计是有讲究的：新线程的栈跟主线程的栈守同一道上限，行为也就整齐了，出了问题也好排查。真要改大小的话，pthread_attr_setstacksize 是正经的口子，咱们在这儿只留一个名字。

您也别被 8 MB 吓着，那 8 MB 是虚拟地址空间里的预留，不是一口气占掉的物理内存。栈跟别的匿名内存一样按需落页：线程真的用到哪一页，内核才真的给哪一页，没碰过的部分只是地址空间里的一段空洞。

> 咱们把术语卡立在这儿：**缺页**。线程摸到了还没落地的页，CPU 陷进了内核，内核把物理内存补上了再放行，缺页指的就是这一来一回。新线程的头几次函数调用、头几层局部变量，都会踩出这样的页来。

预留而不实占，靠的正是虚拟内存的设计：地址只管圈下来，物理的页随用随给。所以咱们开起一条新线程，物理内存的增量远没有 8 MB，实际给出去的页有多少，等一下拿 perf stat 的 page-faults 就能看个大概。

栈之外剩下的还有一串登记：信号怎么安排、清理函数挂哪儿、线程局部存储怎么备，件件都是有人管的。咱们把它们记在心上就好，正文不再逐条展开了。

### 三道闸门

那咱们把线程往多了开会怎样？pthread_create 不是总能成功的，它失败的时候返回错误码，最常见的那个叫 EAGAIN，直白的意思就是资源暂时不够用、回头再试。手册的 ERRORS 节列了三处可能不够的地方，咱们把它们整理成一张表：

| 闸门 | 管的范围 | 在哪儿看 |
|---|---|---|
| RLIMIT_NPROC | 单个用户的进程与线程总数 | `ulimit -u` |
| threads-max | 全系统的线程总数 | `/proc/sys/kernel/threads-max` |
| pid_max | PID 的总量 | `/proc/sys/kernel/pid_max` |

三道闸门是各管一段的，哪一道顶到了，返回的都是 EAGAIN。您拿几条命令就能把自己机器的底摸一遍：

```bash
ulimit -s                          # 栈的上限，多数发行版把它设成 8 MB
ulimit -u                          # 本用户的进程与线程数上限（RLIMIT_NPROC）
cat /proc/sys/kernel/threads-max   # 全系统的线程总数上限
cat /proc/sys/kernel/pid_max       # PID 的总量
```

几条命令花不了一分钟，您却把自己机器的闸门摸了一遍。具体的数字是多少不打紧，要紧的是您知道了闸门在哪儿，往后程序起线程起不动的时候，您也就知道该去哪儿查了。

### 掐一次表

咱们光说贵不贵没有意思，掐一回表就好了。配套代码仓里现成的基准就是给这件事备的。

它干的活儿您一看就懂：起一千个“只做一次加法”的空线程，一个一个地 join 收尾，咱们拿总时间除以一千。同样的活儿，咱们再直接调用一千次当对照。

```bash
# 编译跑起来，数字随机器浮动，看量级就好
g++ -std=c++17 -O2 -Wall -Wextra -pedantic -pthread 03_os_threads_and_cost.cpp
./a.out 1000
```

```cpp
// 摘自代码仓的 03_os_threads_and_cost.cpp
const auto start = std::chrono::steady_clock::now();
long long sink = 0;
for (int i = 0; i < 1000; ++i) {
    std::thread t([i, &sink] { sink += noop_task(i); });  // 空任务：一次加法
    t.join();  // 做完就收，量的是“创建加收尾”的一整个来回
}
const auto stop = std::chrono::steady_clock::now();
// 对照组：同样的循环不起线程，直接累加，两版各除以 1000
```

两边的量级差多少，跑一遍就有数了：直接调用是纳秒级的，起线程是微秒级的，中间隔着的是实打实的数量级差距。sink 的校验咱们也留了一手，两版算出的总数对不上就报错，防的是编译器把活儿优化没了。

> 边栏：计时咱们选了 steady_clock，因为它不受系统时间跳变的影响。wall clock 半夜里校时一跳的话，数据就废了，clock_gettime 的手册页把这件事讲得很清楚。

Williams 在《C++ Concurrency in Action》的第一章里给过定性的一句，说任务要是三两下就跑完了，起线程的功夫反而成了大头，头一篇咱们引过原句，本篇就把那个大头给量了出来。

<!-- 实验回填：1000 次空线程创建加 join 与 1000 次直接调用的 chrono 对比，两版的单次耗时与倍数（本机 g++ -O2 -pthread） -->

> 边栏：这个数里其实混了 join 的等待、调度器的安排，还有循环自己的开销，量的并不是“纯创建”。测量其实从来不纯，您能把混进来的东西说清楚，数就有用了，练习 1 练的正是这个。

咱们把这个量级放回任务粒度的语境里，头一篇立下的要求在这儿就落地了：任务本身的计算量，应当显著贵过创建和调度它的开销。一次加法是纳秒级的活儿，配的却是微秒级的启动成本，给数组的每个元素开一个线程的写法就荒唐在这儿，得等两边的比例倒过来才划得来。

创建的价格咱们记下了，接下来该看切换了，那一头才是反复发生的开销。

## 切换：寄存器搬家，缓存变冷

线程创建好了之后，真正反复发生的开销是切换。一个核在同一时刻里跑的线程只有一条，超线程的细分咱们暂且不管，下一个上场的轮到谁，是由内核决定的。

> 咱们把术语卡立在这儿：**上下文**。它指的是某一时刻 CPU 的全套状态：通用寄存器、程序计数器、栈指针，还有页表基址这样的关键寄存器。切换换的就是它：进程也好、线程也好，档案里存的都是这样一套东西。

换场的动作叫上下文切换：把当前线程的寄存器状态存回它的档案，再恢复下一条线程的寄存器状态，跳到它上回停下的位置接着跑。听着是挺平淡的，咱们往下看它贵在哪儿。

### 什么触发了切换

触发切换的原因不少，咱们捡三样常见的说：时间片用完了要切，线程阻塞在 I/O 上的时候要切，更急的线程到了也要切。

> 咱们把术语卡立在这儿：**时间片**。调度器分给每条线程的 CPU 时间是按小份发的：一份就叫一个时间片，用完了内核就考虑换人。它的长短由调度器按负载动态地定，并不存在写死的毫秒数，所以咱们不背它的具体值。

对写程序的咱们来说，两行代码之间的任何一个位置都可能被切进去，您是预测不了的。您回忆一下 ch00/02 里说的“并发 bug 难复现”，根子之一也就在这儿了，交错的窗口是调度器随手开的。

本篇咱们把切换本身的价格弄清楚，调度的门道留给后面的一节。把贵在哪弄明白了，再谈怎么省也就有了底，这一步是正确性之外咱们能做的最实的一步。

咱们还得记下一层背景：调度是全局的，不是咱们的程序独享的。机器上别的进程也在排队，咱们量出来的数里，别人家的份额也掺在里面。

### 直接开销与间接开销

咱们把直接开销摆出来看，它是看得见的那部分：寄存器要一份一份地存好，再一份一份地恢复回去。x86-64 的通用寄存器有十六个：这部分算是小头，浮点与 SIMD 的状态才更有分量。

咱们把镜头再拉近一层：开了 AVX-512 的机器上，光 ZMM 寄存器组就有 32 个 512 位宽的寄存器，状态本身的尺寸约是 2 KB，保存与恢复都是实打实的数据搬运。

您可能会想，2 KB 也不多啊。咱们也承认不多，贵的地方不在搬运上。

贵的大头在间接的那部分，咱们把镜头切到新线程这边：切换一回来，它面对的就是一个刚刚还属于别人的世界。您可以把 TLB 想成页表的缓存：里头存着的映射多半是前一条线程的，得一条一条地换掉，新线程自己的数据也大概率不在眼前这个核的缓存里，是冷的。

缓存怎么分层、多核之间的一致性怎么维持，那是 [ch03 头一篇](../ch03-atomic-memory-model/01-cache-foundation.md) 的正题，本篇咱们只把一件事记下来：一次切换，会把您攒下的热乎劲儿冲掉一大截。

切换还分同核与跨核的两种，跨核的还要更贵一些：寄存器之外，又搭上了另一份冷的开销。perf stat 的输出里有一行 cpu-migrations，数的正是线程在核之间搬家的次数，咱们等一下就能看到它。

### 外部参考与本机重测

> 外部参考咱们只取量级：同一进程内两条线程之间的直接切换，公开实测大约是 1.2 到 1.5 微秒（把线程绑在固定核上的时候），不绑的时候大约 2.2 微秒。数字来自 Eli Bendersky 2018 年在一台 Haswell i7-4771 上的测量，方法透明而环境单一，跟您手头的机器没有直接的关系，咱们只拿它定个量级。全卷的纪律也是这么立的：别人的数字进参考框，自己的数字自己测，本机的重测放在练习 3。

<!-- 实验回填：本机乒乓法重测的每回合耗时（两线程用一个 atomic 布尔交替翻转百万次），与 Bendersky 参考值的对照 -->

> 边栏：参考框里绑核的版本会便宜一些，原因本篇就不展开了。把线程绑在某个核上（affinity）是性能实测里的常用手段，正主在 [ch04 的 perf 主课堂](../ch04-concurrent-data-structures/02-lock-free-stack-and-perf.md) 与 Lab 04，咱们在这里只把名字记下。

还有一样要想在前头：perf stat 数的切换是次数，不是单次的耗时，拿次数是乘不出时间来的。单次的耗时得靠专门的设计去量，练习 3 的乒乓法就是最小的一版，咱们把这件事记在练习里。

## 内存足迹：一条线程占多大地方

内存那一头咱们单独开一节算。一条线程的常驻足迹里都有什么呢？档案占的是几百字节到几 KB，栈是按需落页的，落了的页才算数，内核那边还有一份自己的内核栈，也是 KB 级的量级。零零碎碎地加起来，常驻的部分不算吓人。

> 边栏：内核栈与用户栈是两回事：内核栈是线程陷进内核办事时用的栈，它是跟着线程走的，不归咱们的代码直接碰。您只要记得一条线程在内核那边也有一份 KB 级的固定家当就好了。

可地址空间里的预留是真的。按常见的 8 MB 算，一千条线程就是 8 GB 的预留，一万条就是 80 GB 的量级。64 位机器的地址空间倒是装得下，闸门却多半在半路就把您拦下了，就算闸门放行了，切换的开销也早把收益吃光了。

您想亲眼看看也有办法，proc 文件系统把答案摊在那儿了：

```bash
# 换成您自己程序的 pid；Threads 那行数的是线程条数，VmRSS 数的是常驻内存
grep -E 'Threads|VmRSS' /proc/<pid>/status
```

您起了十条线程再去看一眼，Threads 那行也就跟着变了：十条新线程加上主线程，数出来的就是 11，这是咱们能直接观察到的“线程是真实的物件”的证据。VmRSS 的涨落跟栈的落页是连在一起的，您起的线程越多、摸到的页越多，它的数字也就长得越大。

这套观察您随手就能做，也用不上特别的权限，往后您怀疑线程数不对的时候，头一个去翻的就是它。

咱们掂线程预算的时候也是同一套次序：头一道看闸门，第二道看的是预留，末一道轮到的才是常驻。三道都过了关，才轮得到咱们谈线程数合不合理。

## 调度器：线程不是越多越好

切换什么时候发生，谁说了算？咱们把答案立在这儿：现代操作系统普遍用的是抢占式调度，时钟中断定期打断 CPU 的那一下，内核会借机重新挑下一位上场的线程，不管当前的线程愿不愿意。

> 咱们把术语卡立在这儿：**抢占**。内核可以把正在跑的线程中途换下场，不必等它把手里的活儿干完，换场的时机是由内核定的。它跟协作式调度是正好相反的两回事，协作式的写法得等线程自己交出 CPU。桌面与服务器上的主流系统都是抢占式的，所以咱们的程序随时可能被暂停或续上，时机不归咱们管。

咱们把 Linux 这边的现状用一句话交代掉。默认的 CPU 调度器在 6.6 版内核里换了人，那一版是 2023 年 10 月发布的，EEVDF 接了 CFS 的班。

您手头的机器只要内核不老，就已经站在 EEVDF 的时代里了。老资料里写着 CFS 的那一批，读的时候您心里得换算一下。

两个缩写您都不用背，本篇要带走的事实只有一条：谁上 CPU、跑多久、什么时候换人，决定权握在内核的手里，而且是随时会变的。想往深处看的，内核文档的调度器目录是正门，链接咱们挂在参考资源里了。

nice 倒是一直都在，-20 到 +19 的取值范围也是老样子，数字低的那一端更受照顾，接口在 EEVDF 接班以后是没有变的。您想体验的话，命令行里敲的 `nice -n 10 ./您的程序` 就是干这个的，加了这个参数的一版就跑得谦让一些，别的线程也就分到了更多的档期。

线程为什么不是越多越好？咱们现在就能讲开了：核就那么几个，线程数远超核数的时候，切换也就变得频繁了，CPU 的一部分时间花在了搬家上，真正干活的时间反而被挤掉了。

排队的关系咱们也能粗略地想：就绪的线程一多，每个核的身后都排起了队，时间片一到就得换人了，换得越勤的时候，咱们在切换一节里算过的那笔间接开销就越是要付。极端的例子 [头一篇](./01-why-concurrency.md) 插过路标：一连接一条线程的 echo 服务，上万个连接对应的就是上万条线程，光切换和栈就够咱们喝一壶的，正解是事件驱动或者协程的路线，那是 [ch06](../ch06-async-io-coroutine/01-coroutine-basics.md) 的地盘。

所以工程上的常见做法是反过来的：咱们固定开一小撮线程，活儿是排队送过去的，那就是 [ch05 的线程池](../ch05-future-task-threadpool/03-thread-pool.md)，或者干脆用协程的写法，把数量的压力挪到用户态里去。

线程数的具体选法也有讲究，不过那是 ch05 的正题，咱们本篇只立下方向：线程宁可少而常驻，也别开一大批来回地切换。

## perf stat：把开销打印出来看

开销聊了这么半天，咱们给出的全是定性。把它们变成能看的数字，perf 是 Linux 上的正牌工具，本篇请您认识它最小的那一块：perf stat。

Brendan Gregg 的 perf 教程页对它的介绍就一句，说它统计并汇总关键的 CPU 计数器。他的站上还有一页 linuxperf.html 的性能门户，您搜 perf 的时候搜出来的多半是它，记例子的是 perf.html 这一页，链接咱们挂在参考资源里了。用法摆出来您就明白了：

```bash
# 被测对象用配套仓里的基准（普通构建就好，perf 不与 sanitizer 版共用一个二进制）
perf stat ./os_threads_and_cost
```

命令跑完了以后，它会把一张小表打到您的终端上，咱们挑默认输出里最有用的四行来认：

| 输出行 | 它数的是什么 |
|---|---|
| task-clock | 这次运行占掉了多少 CPU 时间 |
| context-switches | 期间发生了多少次上下文切换 |
| cpu-migrations | 线程在核心之间搬了多少次家 |
| page-faults | 缺页次数，栈按需落页就计在这儿 |

默认输出里还有 instructions 与 cycles 一类的行，它们更贴近 ch04 的口味，本篇咱们暂不碰。您把四行看熟了，别的行往后自然就认识了。

### 读法：拿来做对照

读法是拿来对照的。您跑两个版本的程序，把这四行数字摆在一起看涨落：切换次数翻了几倍，缺页多了多少，开销的故事就从感觉变成了记录。

咱们把它当开销计数器来用，恰好接住前面的两节：创建一节说的按需落页，对应的是 page-faults，切换一节说的搬家，对应的是 context-switches，跨核的搬家则记在 cpu-migrations 里。四行都各就各位了，前面的定性就都有了着落。

您要嫌一遍的数不稳，perf stat 的 `-r 5` 用法会把基准连跑五遍，均值和波动就都交给您了。数字跳得厉害的机器上，咱们下的判断也得跟着谦虚，波动告诉咱们的就是这件事。

<!-- 实验回填：perf stat ./os_threads_and_cost 的默认输出原文（四行的真实数字），以及本机 perf 的安装路径与版本 -->

一句实话也得说在明处：perf 不是哪儿都预装的，WSL2 里它是常常缺席的，装好了的环境也可能因为 perf_event_paranoid 的限制，让一部分事件看不到了。工具到不了的地方，咱们卷里的替代路线是 chrono 基准加 sanitizer：掐表的事归 chrono，看正确性的活儿归 TSan 与 ASan。

> 边栏：跟 sanitizer 的二进制别混着用，这是咱们卷里的固定做法：TSan 版本自己在代码里插了簿记，咱们拿 perf 去数它的话，数出来的多是工具自己的动静。您要跑 perf，就用普通构建的二进制好了。

顺路咱们再认两样工具：perf top 交互式地看当下的热点，top -H 看每条线程各自吃了多少 CPU，它们都不在本篇的展开范围里。采样的主课堂（perf record 与 report）在 [ch04 的无锁栈篇](../ch04-concurrent-data-structures/02-lock-free-stack-and-perf.md)，伪共享（各写各的数据，却挤在同一个缓存行上）的现场重测也放在同一篇里。

咱们临走还登记一个名字：futex，Linux 上 mutex 的实现核心，无竞争的时候全在用户态、真有竞争的时候才进内核睡等，深讲归 [ch02 的同步原语工具箱](../ch02-mutex-condition-sync/05-sync-primitives-toolkit.md)。

## 本篇收进包里的东西

- `std::thread` 在主流平台是 1:1 模型，一条用户线程对一条内核调度实体，创建走的是 `clone()` 系统调用。
- 创建是微秒级的：一次系统调用、一份内核档案、一块按 RLIMIT_STACK 预留的栈，多数发行版把它设成 8 MB，按需落页。
- 切换也是微秒级的，寄存器搬运是小头，TLB 与缓存变冷才是大头。
- 线程数的闸门有三道：RLIMIT_NPROC、threads-max、pid_max，顶到了 pthread_create 就返回 EAGAIN。
- perf stat 的四行：task-clock、context-switches、cpu-migrations、page-faults，拿它们做对照，开销从感觉变成记录。
- futex 也登记在案：无竞争的加锁解锁全在用户态办完，进内核的才是慢路径，正源在 ch02 的工具箱。

咱们把三样开销也收成一张速查表，量级走的是定性口径：

| 开销 | 量级 | 在哪儿看 |
|---|---|---|
| 创建（系统调用加栈） | 微秒级 | chrono 基准，练习 1 |
| 切换 | 微秒级 | perf stat 的 context-switches |
| 常驻内存 | KB 级，预留是 MB 级 | /proc 的 status 页 |

表里的三行都指回了正文的小节，您忘了哪一行的来路，回小节里翻一遍也就想起来了。

## 练习

### 练习 1：给创建成本掐一次表

编译运行配套仓里的 `03_os_threads_and_cost.cpp`，记下两版的单次耗时与倍数，把数字填回本篇的占位里。然后您把次数换成 100 与 10000 各跑一遍，看看量级是不是稳的。做完之后咱们再想一步：起线程的那一版里，除了创建本身，这个数还混进了什么？掐表一节的边栏点过名，您把它们认出来。

有 perf 的机器上请您加做一步：拿 perf stat 跑同一个基准，把 context-switches 的数字跟您起的线程次数对一对，看看两边是不是同一量级的。这一步练的是计数器与代码对得上号的手感，往后读任何工具的输出都用得上它。

报数的方式也讲究：请您把两版的数都记全，光留一个倍数是不够的。把原始数留下了的话，往后换机器重跑的时候才有得对。

### 练习 2：读一回 pthread_create 的手册

打开 man7.org 上的 pthread_create(3) 手册页，本机敲 `man pthread_create` 也是一样的，请您回答两个问题：默认栈大小是从哪个 limit 来的？返回 EAGAIN 的条件列了哪几条？然后把本机的 `ulimit -s`、threads-max、pid_max 都查一遍，跟手册里的条款对上号才算完。练的是查一手资料的手感，这比背博客可靠多了。

要是您还有余力，请把 clone(2) 的手册也翻到 CLONE_VM 的那一段，看看 pthread 用的标志跟本篇点出的三个名字对不对得上。细读是不必的，您认个脸就算达标了，往后咱们在别的地方还会读到它们。

对答案的时候请您留意 ERRORS 一节的措辞：手册说的是可能的原因，不是必然的判决。哪一道闸门真顶到了，还得拿机器上的数字来认。

### 练习 3：乒乓法测切换

咱们用两条线程和一个 `std::atomic<bool>` 就能搭起测切换的台子：线程 A 把旗子设成 true，等它变回了 false 再走下一步，线程 B 做的正好是反过来的一半，咱们让它往复一百万个回合。咱们拿总时间除以回合数，单个回合的成本也就出来了，再拿它与本篇参考框里的数字对照量级。

做完请您再追问一句：这个数里混了哪些不属于切换本身的开销？atomic 的读写、循环的判断，全都混在里头了。创建一节的边栏说的也是这个道理：您能说清混进来的都是什么，这个数就有用了。

请您把测完的数记到参考框的旁边：同一台机器上，乒乓的每回合耗时与创建的耗时各自是多少，两者的比例本身就有讲头。机器换了一轮之后再记一轮，比例是不是稳的，比单个的数更值得看。
