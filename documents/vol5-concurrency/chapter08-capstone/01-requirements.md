# 题目与行为要求

单元七收尾的时候留过话：下一站是单元八的结课作品，一个小型任务处理程序，题目与行为要求到时候写出来，咱们在那里见（收尾在[《把协程组织成可完成的任务》](../chapter07-coroutines/04-task-type)）。现在咱们就站在那里。本篇把考卷立起来：题目是哪道、行为要求有哪几条、每一条在 8.4《提交验证与设计说明》用什么手段验收，一次交代清楚。怎么实现，本篇一个字不给，实现从 8.2 起，归您。

考察点也要摆明白。读完前七个单元，您手里存下了六样东西。线程与生命周期在单元一，互斥与共享数据的保护在单元二，条件变量与等待的结束路径在单元三，future 与结果的传递在单元四，原子操作与内存序在单元五，协程在单元七。结课作品不教新东西，它把六样摆上桌，让您按需取用，哪些用、哪些不用、挑与不挑的理由，8.2《自行完成并发设计》交设计说明时给出。用到哪样，本卷对应的单元已经替您把机制备齐，本篇不再重复讲机制。单元六给的是验收手法，不是机制，它们住在 8.4 的验收里。

素材来自旧目录 exercises 的《[Capstone: Mini Concurrent Runtime](../exercises/06-capstone-mini-runtime)》，它让读者拼一个 mini 并发运行时，epoll、Channel、线程池、协程调度器，全家桶一起上。改造的方向咱们定过：业务只留对一批数据做计算，网络与事件循环的复杂度全部撤掉，旧文的指标采集也一起撤了，把练习时间留给并发设计本身。收益的测量不跟着旧文走，归 8.4 的计时架。旧文追问的三个工程问题倒是一直保留：组件之间怎么连接、系统怎么停止、错误怎么传播，它们换了一身衣服，住进本篇的行为要求里。

本篇是题目篇，正文不带实现。接口骨架与对照程序都收在 `code/examples/vol5/chapter08/`，可在本页直接运行（WSL2，16 逻辑核，GCC 16.2.1 20260810，2026-11-17）：骨架只求编译通过，对照程序用 `g++ -std=c++20 -O2 -pthread` 跑出读数。工具版本的断言我按 cppreference 核对过（2026-11-17 访问），出处收在参考资源里。

## 题目：一个小型任务处理程序

题目一句话说得完：写一个小型任务处理程序，生产者往里提交任务，工作线程把任务领走执行，程序把结果汇总起来，并且支持按条件停止。一句话之外，咱们把考卷的内容铺开，铺到您动手的时候不必回头问题目本身。

### 考卷里的数据与任务

数据没有真业务，就是一批编号，从 0 到 n 减 1，n 由命令行给进来。编号 i 的任务干一件事：算出 i 的平方，交回 long long。有些编号注定失败：凡是 13 的正倍数，任务一跑就抛出 `std::runtime_error`。挑 13 有来历，单元七的实验里 boom(13) 已经替咱们抛过一回同样的异常（见[《把协程组织成可完成的任务》](../chapter07-coroutines/04-task-type)），考卷把注定失败的名额继续交给 13 的倍数。

### 提交、执行与汇总

提交方在一条自己的线程上把 n 项任务逐个交给程序，工作线程按给定的数量同时开跑。谁领到哪一项、两拨人快慢如何，都是运行时的事，考卷不替您安排。提交与执行注定并发，它们中间必须有安全碰头的地方。碰头的地方长什么样、队列自己写还是拿标准库的现成工具凑，设计归您，8.2 交代理由。

收场之后程序交汇总。成功项的结果累加成总数，成功、失败、没轮到做各报一个数。对照值（同一批任务串行算一遍的读数）咱们替您跑好了，数字直接当格式示例用，在下面的输入输出行为里。并发版本的汇总要跟对照对得上，对照的手段归 8.4。

### 停止的立场

程序要提供一个提出停止的入口，谁持有它谁就能提。触发器长什么样，考卷不指定：8.4 的测试会注入，真实场景里可能是一条时间上限。停止提出之后的走向，行为要求一节逐句写明，这里只交代立场：收场走协作式，单元一 1.5 的 stop_token 就是照协作式收场的语义造的工具（见[《让工作有序结束》](../chapter01-start-concurrency/05-jthread-and-stopping)），用不用它归您，语义必须达到。

## 行为要求

要求按性质分四路铺开：输入输出、正确性、停止、失败。每一条咱们都配着验收手段写，落到 8.4 的哪里，条目旁边直接标明。写不出验收手段的要求不算行为要求，那是口号，咱们不收。

### 输入输出行为

输入输出咱们定成最瘦的样子。程序从命令行拿两个数：任务总数 n 与工作线程数量 w。数据不从文件读，编号就是输入。收场之后，程序往标准输出交一行汇总，字段与次序照下面的格式来：

```text
total=307615387695 success=9231 failed=769 skipped=0
```

total 是成功结果的累加值。success 是成功的任务数，failed 是失败的任务数，skipped 是没轮到做的任务数。无停止的一轮里 skipped 是 0，上面的数字正是 n 等于 10000 时该有的读数，出自对照程序 expected.cpp 的串行计算（2026-11-17 跑的），不是格式示意。耗时不进汇总行，测量归 8.4 的计时架。格式收得瘦，咱们对照起来才省事。

退出码也归进行为：正常收场，含按停止收场，退出码是 0。失败的任务不算程序错误，它们是考卷里注定会发生的输入，咱们照常交汇总。程序自己出错，线程没能建起来之类，报错退出就好，退出码自定，8.4 的检查只走 0 的路径。

### 正确性标准

对的标准只有一处可依：跟串行对照。咱们用 expected.cpp 把同批编号串行算了一遍，总数、成功数、失败数都报出来了，您交上来的汇总必须跟它一致。计数另有一道守恒检查：收场之后，提交数等于成功数加失败数加没做数，任务一个不丢，丢了去向的要么是重复算的，要么是悄悄漏掉的，两种都算错。

并发自己的正确性再叠一层：同一份程序、同一批输入，重复跑若干轮，汇总轮轮一致。道理单元六讲过，调度器每轮交出来的交错都不同，一次全对说明不了什么（见[《怎样寻找并发错误》](../chapter06-validating-designs/01-finding-concurrency-bugs)）。轮数与工具归 8.4 安排，手法是重复测试加 ThreadSanitizer。写程序的您不用自己跑满轮数，但写法得让它们跑得过：共享的地方要么有锁护着，要么有原子护着，要么干脆不共享，选了哪条路、为什么，8.2 的设计说明交代。

### 停止语义

停止的要求，咱们逐句写在下面，每一句都拿得出测试：

- 提出停止之后，还没被任何工作线程开跑的任务不再执行，全部计进 skipped。
- 已经开跑的任务让它跑完，结果与失败照常进汇总。协作式的道理单元一讲过（见[《让工作有序结束》](../chapter01-start-concurrency/05-jthread-and-stopping)）：程序里没有人有权限掐断别人手里正在做的活，stop_token 就是照协作式语义造的工具。
- 全部收场之后，守恒检查照常成立，程序按正常路径退出，退出码 0。

另有一条时机的说明值得单独写：停止随时可能到来。它可能落在提交进行到一半的时候，可能落在队列里还压着活的时候，也可能落在最后几项刚开跑的时候。8.4 的停止路径测试会在不同时机注入停止（承 6.1 的手法），您得保证程序在哪个时机接到都收得住场。

### 失败处理

失败的路数考卷已经写死，咱们把要求逐条落在纸面上：

- 异常要被程序接住。线程函数里逃出异常的后果是 `std::terminate` 直接把进程带走，单元一 1.3 讲过（见[《第一个 `std::thread` 程序》](../chapter01-start-concurrency/03-first-std-thread)）。任务抛的异常在工作线程内被捕获、被记录，其他任务照常完成。
- 失败要能对上号。失败清单里查得到编号与异常消息，哪一项、为什么，一眼可查。消息用值存，别存指针，异常对象销毁之后消息还得活着。骨架里的 Failure（失败记录：任务编号加异常消息的拷贝）就照它写。
- 失败算正常结果。failed 计进守恒等式，程序照常退出 0。单元四讲过异常经 future 传递的路数（见[《自行传递结果》](../chapter04-organizing-tasks/03-promise-and-future)），失败跟结果走同一条路，送到汇总的人手里。

## 接口骨架：形状参考，不是规定

咱们给练习定过调：提供行为要求，怎么组织任务与数据由读者自己决定。骨架的立场要摆正：它把题目的边界拼成形，免得您动手的时候跟骨架对不上名字。它不规定您的接口，您完全可以扔开它自己起一套，8.2 交代理由即可。

骨架里值得留意的地方，都是行为要求在接口上的投影，咱们挨个看：

- skipped 单独占一个成员。停止后没做的任务必须单独可数，混进 failed 的话，守恒等式还在，串行对照与失败清单的核对都会失真。
- failures 返回拷贝，消息用 `std::string` 存值。异常对象销毁之后消息还得活着，悬垂指针进汇总报告是常见险情。
- request_stop 标了 `noexcept`。提出停止的动作本身不该失败，它也不抛，收场的等待交给 wait，两个入口的分工在接口上就分开了。

## 选做：协程综合扩展

必修的考卷不要求协程。选做的方向单元七已经备好了料：拿 7.4 的教学版 Task 把提交与等待组织成协程，提交方 co_await 任务完成，异常的接力照 7.4 的路数走（见[《把协程组织成可完成的任务》](../chapter07-coroutines/04-task-type)）。做完您会多出一份比较材料：同一道考卷，线程版与协程版的组织差别、谁在等待、等待压在谁身上，它们写进 8.4 的设计说明正好是现成的素材。

边界也交代清楚：选做不影响必修验收，8.4 只按行为要求检查必修部分。完整的协程运行时不进必修，教学版 Task 的差距清单 7.4 列过，足够撑起选做的体量。您想试的话，材料都在单元七，不用回头补课。

## 轮到您动手的时候

1. 把骨架编一遍，命令就在上一节，编过即达标，本篇不要求更多。
2. 环境报个底：您手头的编译器要能吃下 C++20。本篇的验证在 GCC 16.2.1 上做的，别的编译器没试。8.4 交卷时把编译器、标准选项与机器一并写进报告，手法承 6.2 的测量条件（见[《怎样衡量并发带来的收益》](../chapter06-validating-designs/02-measuring-benefits)）。
3. 口头自测：skipped 为什么单独占一个成员？要是混进 failed，坏掉的会是哪条检查？答得出，守恒的要求您就拿住了。答不出，回正确性标准与接口骨架两节再看一遍。
