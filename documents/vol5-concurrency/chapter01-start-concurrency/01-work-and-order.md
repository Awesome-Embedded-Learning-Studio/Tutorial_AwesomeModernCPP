# 讲义还没下完，列表怎么就能滚了

“OI, Charliechen114514，别摸鱼了！赶紧点去网站上下载资料！”，笔者还在念大学的时候，老师说要去某某网站上下载资料，我的同学跟我说到。

可惜，校园网的确不咋好，点个下载几MB的资料，浏览器上方都还有转圈圈的图标。。。然后你骂着：“啊该死啊我的朋友，页面写的一坨也就算了，网速还是饭桶速度！”的翻动网页。。。等下！

停下来。没有发现一个反直觉的事实嘛？在您的印象里，CPU应该执行一个确定的执行流。比如说，当您对着CPU说您做完A，再做B，最后做C，CPU如是说到“好的老大！”，然后闷头开始执行了。但是显然，刚刚的场景下，**你的浏览器正在一边下载东西一边展示你滑倒的界面！**。看起来你的电脑正在同时做着不同的事情！酷炫吧！

## 咱们把屏幕上发生的事写下来，我们就知道不能完全依赖体感来判断实质的并发

为了方便的陈述，笔者决定还是把戏剧性的陈述，给他干掉，用下面的Mermaid图来向我们演示一下事情的顺序。

```mermaid
graph LR
    A["点下载"] --> B["列表滚动"] --> C["讲义下完"] --> D["显示完成提示"]
```

请注意到这里的线性顺序图，我们谈论了事情**发生时刻**的顺序，事情的演进是存在一个过程的。比如说，我们点击下载到浏览器发起请求这一霎那，也不过是Button发起了网络请求的Callback的时间，对吧。但是下载的过程本身，也就是从A到C，背后是网络将内容从远程搬运到这里的时间。**不耽误我们让浏览器的列表滚动。**。

那要是下发的资源本身要是很小呢？内容没多少，您手刚移到滚轮上，说不定就已经下完了，于是您看到的又是另一个顺序。

```mermaid
graph LR
    A["点下载"] --> B["讲义下完"] --> C["显示完成提示"] --> D["列表滚动"]
```

这下看起来事情又是串行的！但是看起来是串行的，但是，更正确的是下载所消耗的时间比浏览器反应过来进行滚动的时间小。您瞧，那也能保证我的列表滚动起来之前，东西下好了。

因此，从上面的现象陈述来看，要是咱们只是**依赖事情的节点而不是事情发生的过程**来思考并发是否需要，或者是并发是否发生，不合理。重点的思考模型在于我上上个重点比较的，“下载的动作不耽误，也不应该耽误我们让浏览器的列表滚动。”

> 如果还是没有理解，没关系，我正式的说：咱们一步一步看：下载收到了一些内容，列表又往下挪一截。再收到一些内容，再挪一截。**同一段时间里，两件事都在往前走，这就是并发本身**。谁也不必把整段时间让给谁。

各位一定要理解这个，这才是**并发编程本身学习**的意义所在。不是**只是让程序变得更快**，而是**让程序本身可以摆脱不必要的等待**。不管是之后我们谈论的基于分治的程序并发优化，还是基于逻辑正交的程序并发优化（比如说我们的例子），都是从这个目的出发的。并发的应用一定是思考“shit bro，这个地方让CPU等待太傻了，时间让出来，丢给别的人干活！”

> 使用上面的例子就是：并发会让下载因此变快吗？不会，您拿到讲义的时刻可能一点儿没提前。想想也是，要传的内容还是那么多，网速也没变，该多久还是多久。并发换来的不是速度，**是正交的，没有关系的另一件东西可以同时一起做**：您手边的事立刻有人做。按一条线的老办法，点完下载就得干等着，滚轮的动作要排到下载收工之后才有人搭理，页面对您来说跟卡死没有区别。现在您能立刻翻列表，已经是您感受得到的实实在在的好处。

::: warning 过了几秒，就算下完了吗？
您可能想，何必等通知，估计个三秒再弹下载完成不就行了？今天网快，三秒碰巧够，提示弹得正合适。明天网络一慢，下载要用四秒，提示三秒就弹出来，明明还差一秒，页面却一口咬定下好了。根子还是咱们刚说的依赖：提示等的是下载确实下完，是事情发生没发生，不是钟表走了几格。只要后一步依赖下载结果，咱们就得等确实下完真的发生，拿固定秒数去猜，总有猜错的日子。
:::
